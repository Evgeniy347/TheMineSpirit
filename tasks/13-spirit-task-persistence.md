# 13 — Техдолг: задача духа переживает выгрузку и перезапуск

Источник: `todo.md` → «В работе и техдолг» («Задача духа не переживает выгрузку чанка и перезапуск сервера:
`SpiritBrain` не сохраняется»); `AGENTS.md` → «Решения пользователя» (дух держит чанки, работает вдали от игрока).
Сейчас `SpiritEntity.addAdditionalSaveData` пишет только инвентарь: после перезапуска сервера, смены измерения или
выгрузки чанка дух стоит без дела, а внешний ИИ-агент (REST, чеклисты 14–15) не знает, что его задача пропала.

Перед работой прочитай `AGENTS.md`, `docs/CONVENTIONS.md` (Быстрый путь — вся логика кроме NBT в `core`; Структура —
`SpiritEntity` и `SpiritBrain` уже собирают несвязанные группы; Ошибки — тихий fallback запрещён),
`docs/TESTING.md` (свойства jqwik, тест обязан уметь краснеть), `docs/GIT.md`. Код: `core/engine/*`,
`core/plan/*` (`PlanParser`, `PlanValidator`, узлы), `neoforge/{SpiritEntity,SpiritBrain,SpiritScripts}`,
`src/test/.../engine/{TaskRunnerTests,TestScripts}`. Публикацию и перезапуск сервера не делать.

**Зависимость.** Чеклист 08 (замечания 11–12: билеты чанков не снимаются при выгрузке и проверяются при загрузке
мира) должен быть влит: без него после настоящего перезапуска чанк духа никто не держит и восстановленная задача
не тикает. Для самой логики сохранения он не нужен — GameTest ниже перезагружают сущность вручную.

## Что должно получиться

- Дух с задачей `sequence[goto A, goto B]` после «сохранить сущность → загрузить» продолжает с `goto B`, а не с
  начала и не стоит: шаги, уже выполненные узлами `sequence`, `repeat`, `fallback`, `parallel`, `condition`, не
  повторяются; условие `condition` второй раз не вычисляется.
- Скрипт, который выполнялся в момент сохранения, создаётся заново и начинает сначала (`goto` пересчитывает
  путь и тайм-аут от текущего расстояния; `follow` ищет цель заново). Счётные скрипты (`chop_tree`, `mine_vein`,
  `gather`) могут сохранить число уже сделанного (`saveState`/`restoreState`), иначе после перезапуска сделают
  `count` заново — это пункт 6.
- Завершённая задача (успех, провал с причиной, отмена) сохраняет только итог: `/spirit status` и REST после перезапуска
  показывают то же, что до него. Отменённая задача не оживает.
- Формат версионированный и проверяемый: сохранённое читается тем же кодом, будущий или битый формат не роняет
  загрузку сущности — задача становится `FAILED` с причиной «не удалось восстановить задачу: …» и WARN в логе.
  Дух без `SpiritTask` в NBT (все существующие духи мира) загружается как раньше, ничего не меняется.
- Стоимость: снимок строится только при сохранении сущности, не в тике.

## Формат (версия 1, решение исполнителя — в пределах этих рамок)

NBT духа получает один ключ `SpiritTask` — строка JSON. Её схема:
`{"version":1,"status":"RUNNING|SUCCEEDED|FAILED|CANCELLED","reason":"…","plan":{…},"progress":{…}}`.
`plan` — тот же JSON плана, что принимает `PlanParser` (ключи из `docs/API.md` → «Формат плана»); `progress` — дерево
того же вида, что и план, с позициями исполнения (индекс шага, число проходов, выбранная ветка, статусы потомков
`parallel`, состояние текущего скрипта). Для завершённой задачи `plan` и `progress` отсутствуют. Версия — число в
JSON, а не в имени ключа NBT. Читатель принимает версии `≤ 1`; новая версия добавляет читателя старой.

      `TaskRunner.restore(TaskSnapshot, ScriptRegistry, ConditionRegistry)`. Восстановленный `RUNNING`-скрипт
      создаётся фабрикой заново, затем `restoreState`. Потомок, уже завершённый в `parallel`, заново не запускается;

      Тесты `TaskRunnerRestoreTests` (на счётных тестовых скриптах `TestScripts`): `sequence[a,b,c]` на шаге 1 → после
      восстановления запускаются только `b`, `c`; `repeat(5)` после 2 проходов — ещё 3; `fallback` на второй ветке не
      возвращается к первой; `parallel(all)` с одним завершённым потомком — второй доделывается, первый не
      перезапускается; `condition` — вычислитель вызван 0 раз; состояние скрипта (`saveState` → `restoreState`)
      доходит до экземпляра; восстановленный `SUCCEEDED/FAILED/CANCELLED` не запускает ничего и сохраняет причину.

      выполнить `t` тиков → `snapshot` → `encode` → `decode` → `restore` → дойти до конца; итоговый статус и список
      завершённых скриптов равны прогону без перезапуска (прерванный скрипт может стартовать на один раз больше).
- [ ] 4. **Тест на масштаб (ядро).** План на предельных 256 узлах глубиной 16: JSON снимка ≤ 64 КиБ, обход при
