## Что должно получиться

Один `SpiritCoordinator` на `ServerLevel` видит состояние всех духов (снимок раз в `SNAPSHOT_INTERVAL_TICKS`),
выдаёт конкретному духу приказ (`CombatDirective` из чеклиста 30 — приказ снаружи тактики духа) и назначение
работы (бронь цели). Тактика духа становится исполнителем решений координатора; локальные рефлексы политик
(чеклист 20) остаются у духа. Ядро — детерминированная чистая логика (`core/coordinator`, без Minecraft), адаптер —
один координатор на уровень.

- **Общее состояние духов.** Снимок раз в `SNAPSHOT_INTERVAL_TICKS`: для каждого `SpiritEntity` уровня — позиция,
  доля здоровья, режим боя, текущая цель/работа, число угроз рядом, атакован ли он сейчас, тик последнего
  наблюдения. Снимок — данные (`CoordinatorState`), не поведение; стоимость в тике — один запрос сущностей уровня
  плюс O(духов), а не каждый тик.
- **Оборона по секторам.** Вокруг защищаемой точки (`defendedPoint`) и в радиусе `DEFENSE_RADIUS` координатор
  делит круг на сектора по числу защитников и выдаёт каждому его пост (стоянку и направление). Каждый защитник
  остаётся в радиусе (пост внутри круга, `setGuardZone`/приказ удерживают его). Защита — приоритет у всех: на
  время обороны каждый защитник получает приказ обороны поверх своей работы.
- **Помощь тому, на кого напали.** Если из снимка видно, что на духа напали (враг выбрал его целью), координатор
  выбирает ближайших свободных защитников в радиусе (не больше `MAX_ASSIST`) и выдаёт им приказ идти на помощь;
  остальные держат свои сектора.
- **Мягкое распределение работ.** Свободным духам координатор выбирает работу с штрафом за толпу: оценка цели
  включает `CROWD_PENALTY × (сколько духов уже идут к ней)`, но запрета нет — при нехватке целей несколько духов
  берут одну (шахту, рубку). Выбор детерминирован и не берёт цель, занятую другим по брони.
- **Брони целей работ.** Общий реестр броней поверх `BuildReservations` чеклиста 29: цель — клетка/дерево/жила
  (`WorkTarget`). Дух бронирует цель перед работой и снимает после; чужая бронь — цель не берётся (в итоге —
  «занято другим духом»); просроченная бронь (`WORK_LEASE_TICKS`) освобождается и перераспределяется. Две души не
  берут одну цель.
- **Тактика духа — исполнитель.** Координатор не ведёт бой и не двигает духов сам: он только выдаёт приказ
  (применяется и снимается одним API `TacticsService`, чеклист 30) и брони. Бой, отход и движение — существующая
  тактика; `LayerArbiter` не меняется (TACTICS уже выше STRATEGY).
- **GameTest.** 3–4 духа на атаку моба у базы — распределение по секторам, все в радиусе; 3 духа в свободном
  режиме на 3 деревьях — не толпятся (каждый своё); тест на масштаб 20 духов — снимок и план не каждый тик.

### Как координатор устроен (предлагаемый механизм)

1. **Координатор один на уровень.** `CoordinatorRegistry` держит по одному `SpiritCoordinator` на `ServerLevel`
   (карта по измерению, как `SpiritChunkTickets`). Тик — из `ServerTickEvent.Post` (образец `RestLifecycle`,
   `TaskWatcher`), только для `ServerLevel`; при остановке сервера/выгрузке уровня координатор снимается. Снимок и
   план пересчитываются раз в `SNAPSHOT_INTERVAL_TICKS`, сброс просроченных броней — тем же тиком.
2. **Ядро — чистые функции.** Снимок → `Coordinator.plan(state, reservations, now)` → `CoordinatorPlan` (оборона,
   помощь, работы). Никакого мира и кэшей внутри: на одинаковом входе тот же выход (детерминизм, свойства jqwik).
   Адаптер собирает снимок из мира, зовёт чистую функцию, применяет результат.
3. **Сектора — геометрия.** `SectorAssigner` делит круг на `n` равных секторов и сопоставляет защитников секторам
   (устойчивое сопоставление по `(угол, id)`, чтобы при выбытии сосед не прыгал через весь круг). Пост — внутри
   радиуса; приказ обороны (`GUARD_AREA`-приказ координатора) держит духа у поста. «Не уходить дальше радиуса» —
   измеряемое свойство постов, а не пожелание.
4. **Помощь — по расстоянию, с ограничением.** `AssistPolicy` берёт не больше `MAX_ASSIST` ближайших свободных
   защитников в радиусе; атакованный не считается помощником. Сектор оставшегося защитника сохраняется, пока
   есть кому держать (ротация защитников — отдельный чеклист).
5. **Работы — оценкой, а не запретом.** `WorkAllocator` для каждого свободного духа считает
   `distance(spirit, target) + CROWD_PENALTY × (уже назначено на цель)` и берёт минимум; при малом числе целей
   несколько духов всё равно получают работу. Бронь (`WorkReservations`) — жёсткое правило только против явного
   конфликта: цель, занятая другим, не берётся. Бронь с тайм-аутом (lease): затянувшуюся работу координатор
   освобождает и перераспределяет.
6. **Приказ — один API.** Применение/снятие приказа — через одно API `TacticsService` (чеклист 30, п. 12):
   координатор не знает, кто отдал приказ (скрипт 30 или он сам), — то же, что и в 30. Приказ выдаётся только при
   смене ситуации (не каждый снимок), чтобы не дёргать тактику.

## Часть А — ядро (`core/coordinator`, без Minecraft)

- [ ] 1. **`SpiritSnapshot` + `SpiritRole`** — снимок одного духа: `record SpiritSnapshot(UUID id, Point pos,
  double hpFraction, SpiritRole role, CombatMode mode, int threatsNear, boolean attacked, Optional<WorkTarget>
  workTarget, long lastSeenTick)`. `enum SpiritRole { IDLE, WORKER, DEFENDER, BUILDING }`. Проверки: `id`/`pos` не
  `null`, `hpFraction` зажат 0..1, `threatsNear ≥ 0`, `lastSeenTick ≥ 0`. Тесты: поля читаются; доля здоровья
  зажимается; `null id`/`pos` — исключение с текстом; роль всегда одна из. Свойство: снимок неизменяем; `attacked`
  согласован с `threatsNear` (атакован при `threatsNear > 0` не обязательно, но `false` при нуле угроз — да).
- [ ] 2. **`CoordinatorState`** — состояние поселения в тик: `record CoordinatorState(Optional<Point>
  defendedPoint, double defendedRadius, List<SpiritSnapshot> spirits, long tick)`. Пустой `defendedPoint` — обороны
  нет; радиус > 0, если точка есть. Доступ: `defenders()`, `workers()`, `byId(UUID)`. Тесты: нет духов; нет точки
  обороны — защитников ноль; радиус ≤ 0 при точке — исключение; `null`-список — исключение; список духов
  упорядочен по `id` (детерминизм). Свойство: `byId` каждого духа находит его же.
- [ ] 3. **`WorkTarget` + `WorkKind`** — ключ брони: `record WorkTarget(WorkKind kind, BlockCoord anchor)`,
  `enum WorkKind { CELL, TREE, VEIN }`. Позиция — якорь цели (клетка/ствол/жила). Тесты: равенство и `hashCode` по
  полям; `null`-якорь — исключение с текстом; вид всегда один из. Свойство: `CELL`/`TREE`/`VEIN` с одним якорем —
  разные ключи (разные цели).
- [ ] 4. **`WorkReservations`** — общий реестр броней (ядро): `reserve(WorkTarget, UUID, long now, long leaseTicks)
  → Outcome` (`GRANTED`, `TAKEN_BY_OTHER`, `TAKEN_BY_SELF`), `release(WorkTarget, UUID)`, `releaseAll(UUID)`,
  `owner(WorkTarget) → Optional<UUID>`, `expire(long now) → int` (сколько броней снято). Просрочка — по дедлайну
  `now + leaseTicks`; повторная бронь того же духа — `TAKEN_BY_SELF` (не новая). Тесты (таблица): свободная цель —
  `GRANTED`; второй дух — `TAKEN_BY_OTHER`; тот же дух — `TAKEN_BY_SELF`; `release` освобождает; `releaseAll`
  снимает все брони духа; `expire` снимает только просроченные; время назад — исключение. Свойства (jqwik):
  **каждая цель занята не более чем одним духом**; после `releaseAll(u)` у `u` броней нет; `expire` не снимает
  бронь раньше дедлайна.
- [ ] 5. **`SectorAssigner`** — распределение защитников по секторам: `assign(Point center, double radius,
  List<UUID> defenders) → List<DefenseAssignment>`; `record DefenseAssignment(UUID defender, Point post, double
  bearing)`. Круг делится на `n` равных секторов, сопоставление устойчиво по `(угол, id)`. Тесты: нет защитников —
  пустой список; один защитник — ровно один пост; два-три — разные сектора; пост при `center` — не вырожден;
  радиус ≤ 0 — исключение; `null`-вход — исключение. Свойства (jqwik): каждый защитник ровно один раз;
  **каждый пост не дальше `radius` от центра**; результат детерминирован (тот же вход — тот же выход);
  при удалении одного защитника остальные посты тоже внутри радиуса (**перераспределение**).
- [ ] 6. **`AssistPolicy`** — помощь атакованному: `assist(UUID attacked, List<SpiritSnapshot> spirits,
  List<DefenseAssignment> posts, int maxHelpers) → List<UUID>`. Берутся ближайшие свободные защитники (не
  атакованный, не занятые боем) не более `maxHelpers`, по расстоянию до атакованного, тай-брейк по `id`. Тесты:
  атакованного никто не защищает — выбран ближайший; `maxHelpers` ограничивает; защитников нет — пусто;
  атакованный не в списке помощников; недетерминированный порядок входа не меняет выход. Свойство: размер
  результата ≤ `maxHelpers`, все — защитники, атакованный не входит.
- [ ] 7. **`WorkAllocator`** — мягкое распределение работ: `allocate(List<SpiritSnapshot> free, List<WorkTarget>
  candidates, WorkReservations reservations, long now) → List<WorkAssignment>`; `record WorkAssignment(UUID spirit,
  WorkTarget target)`. Оценка цели — `distance(spirit, target) + CROWD_PENALTY × (уже назначено на цель)`; минимум
  берётся без запрета; цель, занятая другим по брони, пропускается. Тесты: одна цель, два духа — оба получают её
  (работа есть всем); три цели, три духа у разных расстояний — разные цели; цель под чужой бронью не назначается;
  свободных нет — пусто; тай-брейк по `(оценка, id цели, id духа)`. Свойства (jqwik): каждый свободный дух
  появляется один раз; **нет двух духов на цели, забронированной одним из них**; при числе целей ≥ числа духов и
  равных расстояниях максимум на цель — 1; результат детерминирован.
- [ ] 8. **`CoordinatorPlan` + `Coordinator`** — чистая сборка решений: `plan(CoordinatorState state,
  WorkReservations reservations, long now) → CoordinatorPlan`; `record CoordinatorPlan(Optional<Point>

  наличии точки, помощь атакованным, работы свободным (не защитникам). Тесты: нет точки обороны — оборона и помощь
  пусты; точка есть — все защитники в обороне и в радиусе; атакованный получает помощника; свободные работники
  получают разные цели; защитник не получает работу одновременно с обороной. Свойство: **каждый защитник в
  радиусе**; **каждая цель занята ≤ 1 духом**; детерминизм; при выбытии духа оставшиеся решения валидны
  (**перераспределение**).

## Стоимость в тике

- Снимок — раз в `SNAPSHOT_INTERVAL_TICKS`: один запрос `getEntitiesOfClass(SpiritEntity.class)` уровня плюс
  O(духов) на духа (не скан мира вокруг каждого). Между пересборками координатор не читает мир.
- `Coordinator.plan` — O(духов log духов) на пересборку (сектора, помощь, работы); не в каждом тике.
- Брони — O(1) на `reserve`/`release`; `expire` обходит активные брони только при пересборке снимка.
- Приказ выдаётся при смене ситуации, а не каждый снимок (тактика не дёргается зря); бюджеты самой тактики
  (`EVAL_INTERVAL_TICKS`, `countEntityQuery`/`blockReads`) не меняются.
- Вложенных циклов «духи × духи» и «духи × все сущности» на каждом тике нет; тест на масштаб (п. 20) считает
  операции, не время.

## На согласование

1. **H1 — числа:** `SNAPSHOT_INTERVAL_TICKS = 10` (как `EVAL_INTERVAL_TICKS` тактики), `DEFENSE_RADIUS = 16` (как
   `ALLY_RADIUS` и лимит `follow.radius` из AGENTS.md), `DEFENSE_POST_RADIUS ≈ 3` (радиус удержания поста),
   `WORK_LEASE_TICKS = 600` (30 с), `CROWD_PENALTY ≈ 8.0` (в блоках-эквиваленте), `MAX_ASSIST = 2`,
   `SNAPSHOT_STALE_TICKS = 40`. Цена завышения `SNAPSHOT_INTERVAL_TICKS` — координатор поздно видит угрозу; цена
   занижения — лишние запросы сущностей. Цена большого `WORK_LEASE_TICKS` — долго занятая без дела цель; цена
   малого — работа перераспределяется под руками. Менять числа — только с согласия.
2. **H2 — один координатор на уровень или на поселение.** Решение владельца говорит «на уровень/поселение».
   Первый этап — один на `ServerLevel` (проще и без `SpiritHome`); при появлении дома/лагеря (`todo.md`) —
   разделение по поселению. Цена уровня сейчас — в одном мире все духи в одном плане; цена поселения сразу — нужен
   признак принадлежности, которого ещё нет.
3. **H3 — общий реестр броней.** Один реестр (`WorkReservations`) с ключом клетка/дерево/жила, для клеток
   переиспользует `BuildReservations` чеклиста 29 (П7), или два реестра (стройка и работы) с проверкой обоих?
   Предлагается один: иначе два духа могут взять одну клетку через разные реестры. Цена — сверка с 29; цена
   двух — дыра в конфликте.
4. **H4 — как дух получает работу.** Pull: свободный дух спрашивает `choose(...)` и получает цель (предлагается
   для первого этапа — не трогает планировщик задач). Push: координатор сам ставит план (`SpiritBrain.start`).
   Цена pull — дух сам решает «работать»; цена push — координатор дублирует стратега и трогает движок задач.
5. **H5 — защищаемая точка.** Пока `SpiritHome`/лагерь не в main — точка обороны берётся из `home()` духа
   (заглушка) и/или явной зоны охраны (`setGuardZone`); после «Дом и базы» — из дома/лагеря без правок
   интерфейса. Цена заглушки — сейчас обороняется точка дома духа; цена иного — ждать чеклист «Дом и базы».
6. **H6 — предел помощи.** `MAX_ASSIST = 2` ближайших защитника в радиусе; при большом числе угроз — все
   свободные, но не оставляя сектор пустым (сначала свободные, потом с соседних секторов). Цена малого предела —
   защитники гибнут; цена большого — сектора пустеют.
7. **H7 — порядок с 29/30.** П. 10 и часть Б зависят от 30 (`CombatDirective`, `applyDirective`); сверка п. 4 — от
   29 (`BuildReservations`). Если к финалу их нет в main — всё независимое (пп. 1–9 и их тесты) доводится, а
   зависящие пункты честно помечаются «ждёт 30»/«ждёт 29».
