# 32 — Тактический интеллект: деятельности, распределение по духам, оценка сил, экспедиция в шахту

Источник: `todo.md` → «Тактическое и стратегическое поведение»: «Тактический интеллект: каталог деятельностей с
коэффициентом востребованности, распределение и вытеснение, оценка сил всех духов против врагов, тактики по видам
врагов данными»; «Норма еды на душу населения (что сытнее — приоритетнее) — вход для коэффициентов деятельностей»;
«Экспедиция в шахту: в одиночку не ходят — команда 2–3 духа, зовут игрока; согласился — идут за ним, нет — сами»;
«Приглашение игрока в чат (простой вариант диалога): вопрос висит 3 мин, повтор каждые 30 с, кнопки…». Решение
владельца 13.10: тактический интеллект ЕДИНЫЙ для всех духов и строится поверх координатора (чеклист 31).
Постановка владельца ниже сохранена сжато; чеклист частями А/Б/В добавлен планировщиком.

## Терминология

- **Интеллект один на всех.** И стратегический, и тактический — общие для духов. У отдельного духа своего
  интеллекта нет; остаются только рефлексы политик (чеклист 20: лава, вода, обрыв, крипер и т. п.).
- **Стратегический интеллект** — настоящий ИИ (opencode/Sonnet по REST раз в 1–5 мин, `agents/strategist`,
  docs/STRATEGIST.md): видит поселение, ставит задания конкретным духам в очередь, меняет цели.
- **Тактический интеллект** — полностью детерминированный алгоритм, один на уровень/поселение, поверх
  координатора 31. Задания из очереди стратега исполняются в первую очередь; если очереди нет, интеллект сам
  вычисляет востребованные деятельности и раздаёт их конкретным духам. Слои: политики > тактика > стратегия;
  угроза жизни вытесняет и деятельность, и задание стратега.
- **Деятельность** — вид занятия с общим интерфейсом. Примеры: рубка, переплавка, изготовление инструментов,
  готовка, рыбалка, игра с детьми, прогулка, торговля, защита себя/других, лечение себя/других, бегство,
  строительство. Список растёт, поэтому каждая деятельность — реализация одного интерфейса, а не ветка в коде;
  у детей свой каталог.

## Алгоритм выбора занятий (тактический интеллект)

1. Взять каталог деятельностей (для детей — отдельный каталог).
2. Для каждой деятельности вычислить **коэффициент востребованности** по состоянию поселения: запасы (еды на
   душу, руды, железа, оружия), угрозы, нужды других духов, время суток.
3. **Распределить** деятельности между духами: подходит ли дух (навыки, снаряжение, роль), сколько идти, штраф
   за толпу (чеклист 31: мягкое распределение, бронь целей).
4. **Вытеснение.** Если дух занят, сравнить важность текущего и нового занятия; переключать только если новое
   важнее, с гистерезисом (задания не дёргаются туда-сюда). Задания стратега имеют свой вес, угроза жизни их
   вытесняет.

### Примеры владельца (сценарии для GameTest)

- **а) Угроза во время работы.** Дух собирает пшеницу, к нему идёт зомби. По оружию, здоровью и наличию сундука
  с оружием выбирает: бой, бегство или бег к сундуку за оружием и потом бой. Остальные (плавят, строят)
  отвлекаются только по расчёту; против одного зомби идут один-два подходящих духа, а не все.
- **б) Запаса хватает, нужды в другом.** Пшеницы много, но нет оружия, руды и железа — нужна шахта. В одиночку
  не ходят: команда 2–3 духа и зов игрока. Согласился — идут за ним, иначе идут сами.
- **в) Цель достигнута.** Пшеницы достаточно — сменить деятельность на отдых или игру с детьми.

## Оценка сил (кого в бой, кому бежать)

Отдельный детерминированный алгоритм. Вход — характеристики врагов и духов (здоровье, броня, оружие, чары;
профиль врага из `data/theminespirit/tactics/enemies.json`: hp, dps, скорость, дальний бой, взрыв, полёт, тир;
расстояния до целей). Выход — предсказание исхода и назначение каждому духу: в бой; бежать; бежать за оружием;
лечиться. Число бойцов соответствует силе врага: против одного слабого — один-два духа, остальные работают.
Ядро уже есть (`core/tactics`: `EnemyProfiles`, `ArmorModel`, `EnemyMetrics`, `Assessment`), но оценивает одного
духа против окружения; здесь нужна оценка по всем духам сразу — внутри координатора 31.

## Тактики по видам врагов (предложение главного агента; реализация — tasks/33-defense-algorithm.md)

Тактики хранятся данными рядом с `enemies.json`, а не ветками в коде. Кратко, чтобы не потерять: **зомби/хаск/
утопленник** — ближний бой, против толпы отход в узкий проход, утопленника не преследовать в воде (с трезубцем
— дальняя угроза); **скелет/зимогор** — сближение по укрытиям, со щитом, бой вплотную, зимогор замедляет —
отходить раньше; **паук/пещерный паук** — бой на открытом месте (пауки лазают), днём паука не трогать,
пещерный ядовит — при низком здоровье лечиться; **крипер** — дистанция не меньше радиуса взрыва (политика 20:
9, заряженный 13), бой луком или «удар и отскок», не подпускать к группе и постройкам; **ведьма** — цель
номер один для лучника, уходить от зелья; **эндермен** — не смотреть и не трогать, бой под навесом 2 блока или
у воды; **слизень** — мелких игнорировать, крупных бить по очереди; **фантом** — укрытие под крышей, лук;
**разбойники** — дальники по укрытиям, топорщик опасен вблизи, опустошителя не встречать в лоб; **нижний мир
(blaze, wither_skeleton, piglin_brute) и страж (warden)** — пока только бегство (страж — тихо). Сами правила,
приоритеты целей и инстинкты боя — tasks/33, не здесь.

## Что должно получиться

Один тактический интеллект на `ServerLevel` (как координатор) поверх `core/coordinator`: каталог деятельностей,
коэффициент востребованности по состоянию поселения, распределение по духам с вытеснением и гистерезисом,
оценка сил врагов и духов, экспедиция в шахту командой 2–3 с приглашением игрока. Ядро — чистая детерминированная
логика (`core/intellect`, без Minecraft), адаптер — один интеллект на уровень.

- **Деятельность (Activity).** Интерфейс с `id()`, `demand(view)` (коэффициент востребованности), `eligible(spirit,
  view)` и `order(spirit, view)` (намерение). Первый этап — пять: **рубка, ферма, добыча, отдых, защита**
  (переплавка, готовка, рыбалка, торговля, стройка, игра с детьми, прогулка — расширением каталога без правки
  распределителя). Каждая деятельность — класс, а не ветка в коде.
- **Каталог.** Взрослый и детский списки отдельно; распределитель берёт каталог по признаку духа.
- **Состояние поселения (SettlementView).** Запасы: еды на душу, руды, железа, оружия; угрозы; нужды других
  духов; время суток; население/дети. Снимок — данные, не поведение.
- **Норма еды на душу.** Вход коэффициентов: сколько еды нужно поселению и какая еда сытнее (ранжирование по
  сытности — данные, не ветка).
- **Распределение.** Свободным духам интеллект выбирает деятельность с штрафом за толпу (мягко, как 31); дух
  меняет занятие только если новое важнее на `HYSTERESIS_MARGIN` и прошло `MIN_SWITCH_TICKS` (не мигает).
- **Очередь стратега первой.** Задание из очереди стратега исполняется раньше расчёта; угроза жизни вытесняет
  и его, и деятельность (политики > тактика > стратегия).
- **Оценка сил.** Одна на всех: по врагам и духам решает, кто идёт в бой, кому бежать, кому за оружием, кому
  лечиться; число бойцов соответствует силе врага (против одного слабого — один-два, остальные работают).
  Ядро `core/tactics` переиспользуется, второго движка боя нет.
- **Экспедиция в шахту.** При нехватке руды/железа/оружия — команда 2–3 подходящих духа и приглашение игрока в
  чат кнопками; вопрос висит 3 мин с повтором каждые 30 с, «подождите, я собираюсь (+60 с)» продлевает,
  «идите без меня» закрывает, молчание — духи идут сами; при согласии идут за игроком (`follow`).
- **GameTest.** Распределение разных деятельностей без толпы; вытеснение и гистерезис; оценка сил на одного
  зомби; приглашение и ход в шахту; масштаб 20 духов считает операции.

## Часть А — ядро (`core/intellect`, без Minecraft)

- [ ] 1. **`Activity` + `ActivityId` + `ActivityIntent`** — интерфейс деятельности:
  `interface Activity { ActivityId id(); double demand(SettlementView view); boolean eligible(SpiritSnapshot
  spirit, SettlementView view); ActivityIntent order(SpiritSnapshot spirit, SettlementView view); }`;
  `record ActivityIntent(ActivityId id, Optional<String> script, Map<String, Object> params,
  Optional<WorkKind> workKind)` — `script` пуст у деятельности, исполняемой координатором (защита).
  `enum ActivityId { CHOP, FARM, MINE, REST, DEFEND }`. Проверки: `id`/`view` не `null`; `demand` конечна и в
  `0..MAX_DEMAND`; `script` непуст, если задан. Тесты: значения читаются; отрицательная/`NaN` `demand` —
  исключение с текстом; `script`-пусто только у `DEFEND`. Свойства (jqwik): `demand` детерминирована и в
  `0..MAX_DEMAND`; `order` для подходящего духа ссылается на имя из известного набора (`chop_tree`, `harvest_crop`,
  `mine_vein`, `wait`, `return_home`) или пусто; `eligible` детерминирован (не зависит от порядка вызовов).
- [ ] 2. **`ActivityCatalog`** — каталог взрослых и детских деятельностей:
  `record ActivityCatalog(Map<ActivityId, Activity> adults, Map<ActivityId, Activity> children)`;
  `forChild(boolean)`, `byId(ActivityId)`. Дубли `id` и `null` — исключение с текстом. Тесты: взрослый и детский
  списки не смешиваются; `forChild(true)` не содержит взрослых id; неизвестный `id` — исключение. Свойство:
  обход каталога упорядочен по `ActivityId` (детерминизм). На первом этапе детский каталог пуст, дети — 0.
- [ ] 3. **`SettlementView`** — состояние поселения: `record SettlementView(int population, int children,
  double foodPerSoul, double foodNutritionPerSoul, int ore, int iron, int weapons, int threats, double dayFraction,
  List<SpiritSnapshot> spirits, long tick)`. Производные: `adults()`, `idle()`, `freeWorkers()`, `needsFood(...)`,
  `needsOre(...)`. Проверки: `population/children/ore/iron/weapons/threats ≥ 0`, `children ≤ population`,
  `dayFraction` в `0..1`, `tick ≥ 0`, список не `null` и упорядочен по `id`. Тесты: поля читаются; доли
  зажимаются/отвергаются с текстом; `children > population` — исключение. Свойства: `adults() == population −
  children`; `idle()` — подмножество `spirits`; детерминизм.
- [ ] 4. **`NutritionTable` + `FoodNorm`** — норма еды на душу: `record NutritionTable(Map<String, Double>
  nutrition)` (сытность предмета — данные), `FoodNorm.perSoul(int population, double days, NutritionTable table,
  double ration) → FoodNeed`, `record FoodNeed(long items, double nutrition)`; `FoodNorm.rankScore(table) →
  List<String>` — «что сытнее, то приоритетнее» (сортировка по убыванию сытности, тай-брейк по имени). Тесты:
  население 0 — нужда 0; нужда растёт с населением; сытная еда выше в ранге; пустая таблица — исключение;
  отрицательные входы — исключение. Свойства: `rankScore` отсортирован по убыванию; `perSoul` монотонна по
  населению; детерминизм.

## Стоимость в тике

- Снимок поселения — раз в `DEMAND_INTERVAL_TICKS` (по умолчанию 100, 5 с): один запрос
  `getEntitiesOfClass(SpiritEntity.class)` уровня плюс O(духов) на духа. Между пересборками интеллект мир не
  читает; дух не сканирует окружение сам.
- Запасы — бюджетированное чтение контейнеров за пересборку (`STOCK_READ_BUDGET`), а не каждый тик; результат
  кэшируется до следующей пересборки.
- `TacticalIntellect.decide` — O(духов + деятельностей) на пересборку, не в каждом тике; `StrengthAssessor` —
  O(духов × врагов) один раз за пересборку, а не на духа в бою.
