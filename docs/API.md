# API духов (bridge) — контракт v1

Мост живёт внутри мода и обслуживает контракт встроенным HTTP-сервером JDK. Реализованы все конечные точки:
`capabilities`, `bots`, `bots/{id}`, `observe`, задачи, события и `plan`. Ядро `core` обслуживает контракт, но не
зависит от HTTP.

## Общие правила

- База: `/v1`, формат JSON (UTF-8), кроме потока событий (`text/event-stream`). Ответы идут с
  `Content-Type: application/json; charset=utf-8` и `Cache-Control: no-store`.
- Авторизации нет: сеть доверенная (решение пользователя 2026-10-11); доступ ограничивается адресом привязки
  (`bindAddress` в `serverconfig/theminespirit-rest.toml`) и файрволом.
- Тело запроса — не больше 1 МиБ; больше — 400 `invalid_request`.
- Лимиты запросов (на адрес клиента; адрес в лог не пишется):

| Что | Предел | Отказ |
|---|---|---|
| частота запросов | ведро 40, пополнение 20 в секунду | 429 `rate_limited`, заголовок `Retry-After` в секундах |
| одновременные потоки событий | 4 | 429 `rate_limited` |
| одновременные наблюдения `observe` | 4 | 429 `rate_limited` |
| тело запроса | 1 МиБ | 400 `invalid_request` |
| узлов в плане / глубина | 256 / 16 | 422 `invalid_plan` |
| завершённых задач в реестре | 256 (активные не вытесняются) | старейшие вытесняются |

- Идемпотентность: изменяющие запросы несут `request_id` (UUID). Повтор с тем же `request_id` возвращает
  прежний результат, а не выполняет действие заново.
- Лимиты плана (проверяются валидатором): `repeat.times` 1..64, глубина дерева ≤ 16, число узлов ≤ 256.
- Ошибки — единый объект:

```json
{"error":{"code":"invalid_plan","message":"У скрипта 'wait' не задан обязательный параметр 'ticks' (INT)","details":{}}}
```

`details` — всегда объект (может быть пустым). Тексты — на русском (см. CONVENTIONS.md → «Ошибки»).

| Код | HTTP-статус | Когда |
|---|---|---|
| `invalid_request` | 400 | неверное тело, поле или тип поля; тело больше лимита; 405 (см. ниже) |
| `forbidden` | 403 | зарезервирован, пока не выдаётся |
| `not_found` | 404 | неизвестный путь или дух |
| `conflict` | 409 | состояние не позволяет действие: наблюдение мёртвого духа, дух занят задачей, `request_id` уже использован с другим телом |
| `invalid_plan` | 422 | план не прошёл валидацию |
| `rate_limited` | 429 | больше 4 наблюдений (`observe`) или 4 потоков событий одновременно, либо частота запросов выше лимита |
| `internal` | 500 | сбой моста; сервер не ответил на задачу в серверном потоке за отведённое время |

Известный путь с чужим методом даёт 405 с кодом `invalid_request` и заголовком `Allow` (методы через запятую).
Кода `unauthorized` нет.

## Ресурсы

- **Bot** — дух: `id` (UUID сущности), `name`, `state` (`idle`/`busy`/`dead`), `position` (`[x, y, z]` — блок духа),
  `dimension`, `current_task` (`task_id` активной REST-задачи или `null`; дух, занятый задачей вне REST, `busy` без `current_task`). Состояние `dead` — дух не жив, `busy` —
  у него идёт задача, иначе `idle`.
- **Observation** — текстовая модель мира вокруг духа (не картинка): позиция, инвентарь, перечень блоков
  в радиусе, сущности, контейнеры, `hash`.
- **Task** — поставленная цель и/или готовый план; статус, прогресс, результат.
- **Capability** — описание скрипта: `id`, `summary`, `params` (JSON-Schema), предусловия, эффекты.

## Конечные точки

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/v1/capabilities` | каталог скриптов (для ИИ-планировщика) |
| GET | `/v1/bots` | список духов и их состояние |
| GET | `/v1/bots/{id}` | состояние одного духа |
| POST | `/v1/bots/{id}/observe` | наблюдение мира вокруг духа |
| POST | `/v1/bots/{id}/tasks` | поставить цель (и/или план) |
| GET | `/v1/tasks/{id}` | статус, прогресс, результат |
| DELETE | `/v1/tasks/{id}` | отменить задачу (мир остаётся консистентным) |
| GET | `/v1/tasks/{id}/events` | поток событий задачи (SSE) |
| POST | `/v1/plan` | сухой прогон: проверить план без исполнения |

### GET /v1/capabilities

Каталог только реализованных скриптов (не весь набор из плана): ИИ не должен получить скрипт, который дух не выполнит.
Скрипты идут в порядке полного каталога; `params.required` перечисляет обязательные параметры.

```json
{ "scripts": [
  { "id": "chop_tree", "summary": "срубить деревья",
    "params": { "type": "object", "properties": {
      "species": { "type": "string", "default": "any",
        "enum": ["any", "oak", "spruce", "birch", "jungle", "acacia", "dark_oak", "mangrove", "cherry"] },
      "count": { "type": "integer", "minimum": 1, "maximum": 256, "default": 1 },
      "radius": { "type": "integer", "minimum": 1, "maximum": 32, "default": 16 },
      "replant": { "type": "boolean", "default": false } },
      "required": [] },
    "preconditions": ["есть подходящие блоки в радиусе сканирования"],
    "effects": ["брёвна срублены", "предметы подобраны в инвентарь"] } ] }
```

Навигационные скрипты каталога: `goto_block` (подойти к ближайшему блоку вида; `block` обязателен),
`come_to_player` (подойти к игроку; без имени — к ближайшему), `patrol` (обход точек `points` списком
`"x,y,z"`, режим `loop`/`ping_pong`), `wander` (блуждание в радиусе до истечения `duration_ticks`),
`keep_distance` (держать дистанцию до цели), `walk_careful` (идти к точке, не строя путь через обрыв),
`step_over` (один шаг на соседнюю клетку), `approach` (подойти к цели на стоянку в досягаемости ломки).
Допуск прибытия — 1.25 блока, тайм-аут пути — 40 тиков на блок плюс 200 тиков запаса.

Стоимость движения (тики, предварительно — геймдизайн, меняются только с согласия владельца): шаг 5,
спринт 4, крадучись 15, вода 10, лестница вверх 8 / вниз 4, прыжок 8, падение 8 + 2 за блок; урон падения —
по 1 за блок выше 2 (падение на 2 безопасно, на 3 ранит). Осторожный шаг запрещён при обрыве глубже 2,
заглядывание — 8 клеток пути. Расходные блоки для засыпки и мостов (установка 5 тиков, ценные — 20):
земля, булыжник, гравий, песок и любые доски (`*_planks`). Стоимости решают порядок целей
(ближняя-дешёвая первая) и «ломать или обходить», ванильный поиск пути не перестраивают.

Как скрипты движения работают в игре:

- `return_home` идёт к дому духа; дом ставит команда `/spirit home <духи> set [x y z]` (без координат — на месте духа),
  снимает `/spirit home <духи> clear`; дом хранится в NBT духа (`SpiritHome`). Дома нет — `FAILED` «дом не задан»
  до первого шага.
- `goto_block` просматривает радиус порциями (до 4 срезов за тик), берёт `count` ближайших блоков по стоимости пути
  и идёт, пока любой из них не окажется в досягаемости 4.5 от глаз; блоков нет — `FAILED` «блоков вида X в радиусе R нет».
- `come_to_player` без имени идёт к ближайшему игроку; игрока нет — `FAILED` до первого шага.
- `patrol` проходит точки по порядку; недостижимая точка (дух упёрся и не двигается 40 тиков) пропускается навсегда и
  считается; круг закончен — `SUCCEEDED`, все точки недостижимы — `FAILED` с числами «прошёл N из M точек».
- `wander` выбирает точки по сиду духа в радиусе от старта на твёрдом полу без опасных соседей, до истечения времени.
- `keep_distance` не заканчивается, пока цель жива: раз в 10 тиков сравнивает расстояние с `distance`; дальше
  `distance + 1` — подходит, ближе `distance` — отходит. Цель — имя игрока или UUID сущности.
- `walk_careful` идёт как `goto`, но при каждом построении пути отказывает, если путь не доходит до цели или в
  ближайших 8 клетках есть спуск глубже 2 блоков; дух при отказе стоит. Ванильный поиск пути и так не спускается
  глубже `MAX_DROP`, поэтому осторожный шаг отличается быстрым отказом «недостижимо осторожным шагом» вместо
  застревания у края.
- `step_over` шагает на соседнюю клетку на той же высоте или на 1 выше, если на ней можно стоять; иначе `FAILED` без движения.
- `approach` выбирает стоянку (`StandChoice`) и идёт к ней; если путь к стоянке не удался, пробует следующую (до 3);
  стоянки нет — `FAILED` «подойти некуда».

Скрипты стройки и земляных работ (`place_block`, `fill`, `clear_area`, `dig_area`, `build_schematic`):
ставят и ломают блоки порциями по одному за тик, снизу вверх. Материалы — только из инвентаря духа;
нехватка — `FAILED` с числами (`have`/`missing`), автоматической закупки нет. Свои поставленные блоки дух
помечает и может разобрать; постройка игрока защищена. Лимиты: сторона куба `dig_area` 1..16, объём
`fill`/`clear_area`/`dig_area` не больше 4096, схема не больше 32³ и 4096 блоков; превышение отвергается
до первого изменения мира.

- `place_block` (`block`, `x`, `y`, `z`) — поставить один блок. Отказы с причиной: место занято, нет опоры,
  далеко (подходит сам, недостижимая стоянка — `FAILED`), защищено, нет материала («нужно 1, есть 0»).
- `fill` (`block`, `x1..z2`) — залить коробку (углы в любом порядке). Ячейки духа ставятся последними;
  если коробка не выпускает духа — сначала выходит наружу, иначе колонка пропускается с записью в итог.
- `clear_area` (`x1..z2`) — убрать ломаемое; неразрушимое, защищённое и небезопасное (рядом жидкость,
  опора под ногами) пропускается со счётчиком; если не убран ни один — `FAILED` с числами. Дроп подбирается.
- `dig_area` (`x`, `y`, `z`, `size`) — то же, но куб со стороной `size` от минимального угла.
- `build_schematic` (`file`, `x`, `y`, `z`) — постройка по файлу
  `data/theminespirit/schematics/<file>.json`: `{"version":1,"size":[sx,sy,sz],
  "blocks":[{"pos":[dx,dy,dz],"block":"minecraft:cobblestone"}]}`, якорь в `x,y,z`, порядок снизу вверх;
  уже стоящие нужные блоки пропускаются без расхода. Ошибка формата останавливает старт громко.

Итог стройки (`result` успешной задачи) — объект со счётчиками:

```json
{ "placed": 8, "removed": 0, "skipped": 0, "failed": 0, "have": 8, "missing": 0, "block": "cobblestone" }
```

`block` — вид блока (у `clear_area`/`dig_area` с разными видами — пустая строка). У проваленной задачи
`result` пуст (`null`), числа — в `error`. Прогресс `done`/`target` есть у всех пяти (блоки обработано/всего).

### GET /v1/bots и GET /v1/bots/{id}

`{id}` — UUID сущности духа. Неизвестный `id` (в том числе не UUID) — 404 `not_found` с `id` в тексте.

```json
{"bots":[{"id":"6f1c2d3e-0000-4000-8000-000000000001","name":"spirit","state":"idle","position":[10,64,-3],"dimension":"minecraft:overworld","current_task":null}]}
```

`GET /v1/bots/{id}` возвращает один такой объект без обёртки `bots`.

### POST /v1/bots/{id}/observe

Снимок идёт на серверном потоке по частям (несколько тиков) и не пишет ничего духу. Запрос строгий: тело пустое (все
умолчания) или JSON-объект только с полями ниже; неизвестное поле, неверный тип, значение вне границ и повтор поля —
400 `invalid_request` с названием поля и допустимыми значениями, неверный JSON — 400 с позицией ошибки (строка и столбец).

`filter` применяется к `blocks` (те же шаблоны со `*`, что у `scan`): в ответе остаются только совпавшие блоки.
Одновременно крутятся не больше 4 наблюдений; запрос сверх предела — 429 `rate_limited`, повторите позже.

| Поле | Тип | Умолчание | Границы |
|---|---|---|---|
| `radius` | целое | 8 | 1..32 |
| `filter` | массив строк-шаблонов | `[]` | до 16 шаблонов, каждый не пуст и ≤ 64 символов; символы a-z, 0-9, `_ : . / -` и подстановка `*` |
| `include_entities` | bool | `true` | `false` — список `entities` пуст |

Запрос:

```json
{ "radius": 32, "filter": ["*_log", "*_ore"], "include_entities": true }
```

Ответ (`bot` — `id` духа):

```json
{ "bot": "6f1c2d3e-0000-4000-8000-000000000001", "tick": 123456, "pos": [10, 64, -3], "radius": 32,
  "inventory": [ { "item": "oak_log", "count": 5 }, { "item": "iron_pickaxe", "count": 1 } ],
  "blocks":    [ { "item": "grass_block", "count": 340 }, { "item": "oak_log", "count": 12 } ],
  "entities":  [ { "type": "minecraft:cow", "pos": [14, 64, -1], "distance": 5.0 } ],
  "containers":[ { "type": "minecraft:chest", "pos": [8, 63, -5] } ],
  "hash": "<64 hex-символа SHA-256 от картины мира: без tick и distance>" }
```

### POST /v1/bots/{id}/tasks

Запрос: нужен `goal` или `plan` (план выигрывает, `goal` остаётся подписью). Поля: `request_id` (UUID, обязателен),
`goal` (строка до 500 символов), `plan` (дерево плана), `params` (необязательно: объект из строк и целых — параметры
цели для планировщика, например `{"target":"Steve"}` для «следуй за мной»). Неизвестное поле — 400 `invalid_request`.

```json
{ "request_id": "3f1c...", "goal": "найди руду",
  "plan": { "type": "sequence", "steps": [
    { "type": "script", "script": "scan", "params": { "radius": 32, "filter": ["*_ore"] } },
    { "type": "script", "script": "mine_vein", "params": { "ore": "iron", "count": 3, "radius": 16 } } ] } }
```

Ответ `202 Accepted`:

```json
{ "task_id": "t-42", "bot": "6f1c2d3e-0000-4000-8000-000000000001", "state": "accepted", "request_id": "3f1c..." }
```

- План проверяется по каталогу **реализованных** скриптов; цель без плана планирует резервный планировщик
  (`FallbackPlanner`, LLM в моде нет). Непонятная цель, нереализованный или неизвестный скрипт, лишний параметр,
  нарушение лимитов, «следуй за мной» без `params.target` — 422 `invalid_plan` с причиной.
- Идемпотентность: повтор с тем же `request_id` и тем же телом возвращает прежний ответ `202` (та же задача, дух не
  перезапускается), даже если дух всё ещё занят этой же задачей; тот же `request_id` с другим телом — 409 `conflict`.
  Память — последние 1024 `request_id`; вытесненный считается новым.
- `{id}` духа в пути приводится к каноническому UUID в нижнем регистре: регистр не создаёт второй задачи.
- Один дух — одна активная задача, очереди и вытеснения нет. Дух занят своей REST-задачей (409 с `task_id` текущей) или
  задачей вне REST, например командой `/spirit` (409 «поставлена вне REST») — 409 `conflict`.
- Реестр задач живёт в памяти: после перезапуска сервера он пуст, старые `task_id` дают 404.

### GET /v1/tasks/{id}

```json
{ "task_id": "t-42", "bot": "6f1c2d3e-0000-4000-8000-000000000001", "state": "running",
  "goal": "найди руду",
  "progress": { "step": 2, "total_steps": 2, "current_script": "mine_vein", "done": 1, "target": 3 },
  "result": null, "error": null }
```

`state`: `accepted` / `running` / `succeeded` / `failed` / `cancelled`. `progress.done` и `progress.target` есть у счётных
скриптов (`mine_vein`, `gather`, `place_block`, `fill`, `clear_area`, `dig_area`, `build_schematic`), у остальных
`null`; у завершённой задачи остаётся последний прогресс, у проваленной —
шаг и скрипт, на которых она упала. `error` у `failed` называет причину; «дух исчез» — дух погиб или не вернулся в
мир за 100 тиков (перезагрузка чанка короче не проваливает задачу). Если духу поставили другую задачу вне REST
(команда `/spirit`, планировщик ИИ), REST-задача закрывается как `cancelled` с `error` «задача вытеснена вне REST».

`result` у `succeeded` несёт итог задачи, у остальных состояний — `null`. Для текстовых скриптов (`chop_tree`
и т.п.) — строка (`«срублено 1 из 1»`). Для скриптов восприятия (`scan_blocks`, `scan_entities`, `sense_hazard`,
`locate_*`, `look_at`, `remember`/`recall`/`recall_all`/`forget`) — JSON-объект (см. схему ниже); у обычного `scan`
без фокуса итога нет (`null`). Итог доступен, пока задача в реестре (реестр очищается при перезапуске сервера).

Схема объекта восприятия (`result.type`):

| `type` | Откуда | Поля |
|---|---|---|
| `blocks` | `scan_blocks` | `blocks[]` (`{item, count}`), `radius` |
| `entities` | `scan_entities` | `entities[]` (`{type, pos, distance}`), `radius` |
| `hazards` | `sense_hazard` | `hazards[]` (`{type, pos, distance}`), `radius` |
| `located` | `locate_*` | `script`, `sightings[]` (`{kind, label, pos, detail}`) |
| `cell` | `look_at` | `script`, `sightings[]` (`{kind, label, pos, detail}`) |
| `memory` | `remember`/`recall`/`recall_all`/`forget` | `script`, `sightings[]` (`{kind, label, pos, detail}`) |

Лимиты итога: строка — не дольше 200 символов, список — не больше 32 записей, объект — не больше 4 КиБ;
превышение обрезается с пометкой `"truncated": true`.

### DELETE /v1/tasks/{id}

Отмена: `200` с задачей в состоянии `cancelled`; дух останавливается, незавершённая ломка блока откатывается (блок цел
или сломан с дропом, трещины сняты). Повторный `DELETE` и `DELETE` завершённой задачи идемпотентны: `200` и текущее
состояние. Неизвестная задача — 404.

### GET /v1/tasks/{id}/events (SSE)

`Content-Type: text/event-stream`. Первым кадром идёт текущее `state`, затем `progress` (при смене шага, скрипта или
счётчика), `script_failed` и завершающий `state` (`succeeded` / `failed` / `cancelled`), после чего поток закрывается.
Завершающий `state` со `succeeded` несёт `result` — тот же итог, что `GET /v1/tasks/{id}` (см. схему выше); отдельного
события итога нет.
Каждый кадр несёт `id:`; заголовок `Last-Event-ID` продолжает с места обрыва (приходят только более поздние кадры; если
журнал, окно 256 событий, уже вытеснил нужные, или `Last-Event-ID` больше последнего id журнала, сначала приходит
текущее `state`, дальше поток идёт с позиции журнала). Раз в 15 секунд при тишине идёт
`: keepalive`. Одновременно открыто не больше 4 потоков, пятый — 429.

```
id: 3
event: progress
data: {"step":2,"total_steps":2,"current_script":"mine_vein","done":1,"target":3}

id: 4
event: script_failed
data: {"script":"mine_vein","reason":"нет подходящей жилы в радиусе"}

id: 5
event: state
data: {"state":"failed"}
```

### POST /v1/plan

Сухой прогон: валидация плана по каталогу реализованных скриптов без исполнения (для ИИ до постановки задачи). Мир и
духи не затрагиваются, на серверный поток запрос не ходит.

```json
{ "plan": { "type": "script", "script": "goto", "params": { "x": 10, "y": 64, "z": -3 } } }
```

Ответ `200` — `{ "valid": true }`; `422` — объект ошибки `invalid_plan` с причиной; нет поля `plan` — 400.

## Формат плана (дерево задач)

| `type` | Поля | Смысл |
|---|---|---|
| `script` | `script`, `params` | вызов скрипта |
| `sequence` | `steps[]` | шаги по порядку |
| `repeat` | `times`, `step` | повторить шаг |
| `fallback` | `steps[]` | первый успешный шаг |
| `parallel` | `mode` (`all`/`any`), `steps[]` | параллельно |
| `condition` | `check`, `params`, `then`, `else` | ветвление по предикату |

ИИ возвращает только такие узлы со скриптами из каталога. Произвольный код, команды оболочки и
скрипты вне whitelist отклоняются валидатором (`invalid_plan`).
