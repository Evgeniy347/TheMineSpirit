# Живая отладка сервера

Агент подключается к работающему серверу по JDWP, вживляет код в рантайме, сразу видит результат на живом мире и
только потом переносит правку в мод с тестом. Перезапуск для проверки идеи не нужен; перезапуск остаётся для смены
схемы классов и обновления мода.

## Что выбрано

| Слой | Решение | Почему |
|---|---|---|
| Подключение | JDK 21, `-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005` | штатный отладчик JVM, ничего ставить не нужно; сеть домашняя, без туннелей и токенов |
| Горячая замена | свой клиент на JDI, `VirtualMachine.redefineClasses` | работает с `TransformingClassLoader` NeoForge: замена тела метода не трогает загрузчик и трансформации |
| Скрипты без сборки | `LiveShell` внедряется в загрузчик модов, внутри — `jdk.jshell` | у сниппета тот же загрузчик, что у мода: видны `MinecraftServer` и сервисы; compile-on-eval, без `javac` с ПК |
| Вызов сниппета | брейкпоинт в `RestServer.handle` + запрос `/v1/bots` | нужен поток, уже остановленный событием (JDI не даёт вызывать методы на потоке, остановленном вручную); REST-поток для этого безопасен |
| Брейкпоинты | `BreakpointRequest`, `SUSPEND_EVENT_THREAD`, стек и переменные | останавливается только попавший поток; сервер не встаёт целиком |
| Один агент | `flock` на `/opt/minecraft/debug.lock` + аренда `/opt/minecraft/debug.lease` | атомарная проверка и запись; имя держателя и срок; истёкшую аренду можно перехватить |

Инструмент — `scripts/live-debug.sh`; клиент и мост — `scripts/live-debug/` (`LiveDebug.java`, `LiveShell.java`).
Gradle не компилирует их и не кладёт в jar мода.

### Почему не JBR и не эндпоинт в моде

- **JBR + `AllowEnhancedClassRedefinition`** добавляет методы и поля, но требует заменить JVM живого сервера на
  нестандартную и проверить её с `TransformingClassLoader` NeoForge. Обычная замена тела метода уже проверена на
  живом `PositionTrace`; добавление поведения закрывает `eval`, а схему класса меняют редко и с перезапуском.
  Если понадобится: JBR кладётся в `/opt/minecraft/debug/`, сервер запускается её `bin/java` с
  `-XX:+UnlockExperimentalVMOptions -XX:+AllowEnhancedClassRedefinition`; путь отката — вернуть прежний `run.sh`.
- **Эндпоинт `/v1/debug/eval` в моде** потребовал бы ставить на живой сервер отладочную сборку мода, то есть
  публиковать её. Внедрение `LiveShell` через JDI даёт тот же доступ без новой сборки и без правки мода.
- **JShell с `--execution jdi`** умеет только запускать новый процесс по JDWP, а не подключаться к живому серверу.

## Настройка сервера (уже сделана)

`/opt/minecraft/server/user_jvm_args.txt`:

```
-Xms2G
-Xmx4G
-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005
--add-modules=jdk.jshell,jdk.jdi
```

`server.properties`: `max-tick-time=-1`. Иначе ванильный watchdog убивает сервер, если поток тика стоит на
брейкпоинте дольше минуты. Ограничений на длительность остановки нет; откат — вернуть `60000` и перезапустить.

Проверка: `ss -ltn | grep 5005`, в логе `REST-мост слушает 0.0.0.0:8765`. Каталог для отладочных файлов —
`/opt/minecraft/debug/`; замок и аренда лежат в `/opt/minecraft/`.

Если проверке нужна перезапущенная сборка (новая схема классов), её ставит `scripts/publish.sh --temp -y`
из дерева задачи: он же обновляет пак клиента и страницу. Ручное копирование jar в `mods/` запрещено: пак
и страница разойдутся, клиент не пустит. Возврат на main — `scripts/publish.sh -y` из main.

## Команды

| Команда | Что делает |
|---|---|
| `scripts/live-debug.sh lock` | взять замок (держатель — `LIVE_DEBUG_AGENT`, по умолчанию `$USER`) |
| `scripts/live-debug.sh unlock` | снять свой замок; чужой не снимается, истёкший снимается |
| `scripts/live-debug.sh status` | замок, порты 25565/8765/5005, сводка `/v1/bots` |
| `scripts/live-debug.sh start` | поднять сервер (если лежит), `peaceful` и `forceload`, проверить JDWP |
| `scripts/live-debug.sh stop` | снять замок; `stop --server` — штатно остановить сервер |
| `scripts/live-debug.sh init` | внедрить/пересоздать JShell-мост, показать состояние |
| `scripts/live-debug.sh eval '<код>'` | выполнить фрагмент; `@файл` или `-` (stdin) |
| `scripts/live-debug.sh hotswap <класс> …` | `./gradlew compileJava` (если не `--no-build`) и redefine классов |
| `scripts/live-debug.sh break <класс:строка> [-i] [--thread имя]` | брейкпоинт; без `-i` печатает стек и локальные и продолжает |
| `scripts/live-debug.sh classes [подстрока]` | загруженные классы мода и их загрузчики |

Переменные: `LIVE_DEBUG_HOST` (192.168.0.147), `LIVE_DEBUG_PORT` (5005), `LIVE_DEBUG_REST`
(`http://$HOST:8765`), `LIVE_DEBUG_AGENT`, `LIVE_DEBUG_TTL` (4 ч), `LIVE_DEBUG_TIMEOUT` (120 с).

## Цикл

1. `scripts/live-debug.sh lock` — один раз на заход; дальше каждая команда продлевает аренду.
2. Правится тело метода в моде, `./gradlew compileJava` (это делает `hotswap`).
3. `scripts/live-debug.sh hotswap com.theminespirit.neoforge.Класс` — замена на живом сервере.
4. Наблюдение: `tail -f /opt/minecraft/server/logs/latest.log`, `curl $REST/v1/bots`, `eval`.
5. Правка переносится в исходники, закрывается тестом, обычный коммит; `unlock` в конце захода.

Примеры:

```sh
scripts/live-debug.sh eval 'server.getPlayerList().getPlayerCount()'
scripts/live-debug.sh eval 'onServer(() -> server.getTickCount())'
scripts/live-debug.sh eval 'Class.forName("com.theminespirit.neoforge.PositionTrace")'
scripts/live-debug.sh break com.theminespirit.neoforge.board.BoardLifecycle:24 --thread 'Server thread' -i
```

`eval` выполняет каждый полный сниппет по очереди: `import`, объявления, методы, выражения. Строка `=> значение` —
результат, `ошибка:` — диагностика компилятора, `!!` — исключение сниппета. Сниппет бежит на потоке обработчика REST, поэтому
`System.out` идёт в лог сервера, а для работы с миром нужен `onServer(() -> …)`: он отдаёт задачу потоку сервера и
ждёт результат. Переменная `server` — текущий `MinecraftServer`.

## Что проверено вживую (0.1.2657)

- Замок: `agent-a` взял, `agent-b` получил отказ на `lock` и `eval`; `unlock` чужого — отказ; свой — снят.
- Hotswap: в `PositionTrace.tick` заменён текст `[pos]` → `[pos-live]`; через 15 с новый текст появился в
  `logs/latest.log`; после возврата исходника и повторного hotswap в логе снова `[pos]`.
- Eval: `server.getPlayerList().getPlayerCount()` → `0`; `onServer(() -> server.getTickCount())` → тики сервера;
  несколько сниппетов в одном вызове выполняются по порядку.
- Брейкпоинт `BoardLifecycle:21` и `:24`: останов на `Server thread`, стек из 13 кадров, `event` в локальных,
  `cont`. Поток сервера держали остановленным 70 с — сервер не упал, после `cont` тикает дальше (`max-tick-time=-1`).

## Ограничения и риски

- Замена тела метода сохраняет схему класса. Новые методы/поля/иерархия — только перезапуск с новой сборкой (или
  JBR, см. выше). Внутренние классы заменяются вместе с внешним, если уже загружены; незагруженные пропускаются.
- Класс на сервере должен быть собран из того же коммита, что и локальный, иначе `redefine` может отвергнуть
  изменение. Миксины и классы, переписанные трансформерами, не отлаживаются заменой: правка потеряет трансформацию.
- `eval` выполняет код на потоке REST, а не на потоке сервера. Для чтения это безопасно; изменения мира — через
  `onServer`. Долгий/бесконечный сниппет держит поток REST; клиент можно прервать, но в целевой JVM останется
  выполняющийся вызов — тогда поток может остаться «занятым» до перезапуска сервера.
- Если убить клиент во время вызова метода (не дав ему вернуться), JDWP может оставить поток в состоянии
  `ALREADY_INVOKING`. Лечение — перезапуск сервера; поэтому не прерывайте `eval`/`hotswap` без нужды.
- JDWP и REST открыты всей локальной сети без пароля. Сеть считается доверенной; порт 5005 не выставляйте в
  интернет. Порт 5005 даёт полный контроль над JVM.
- Аренда снимается по сроку (4 ч по умолчанию), но не по смерти процесса агента. Продлевайте командами; после
  аварии — `unlock` (истёкшую аренду снимет любой).
- Внедрение моста требует работающего REST-моста (`/v1/bots`): он даёт поток, остановленный событием. Hotswap и
  брейкпоинты от REST не зависят.
- `max-tick-time=-1` отключает защиту от зависания тика для всех, а не только для отладки. Это цена режима
  «сервер — отладочный»; после отладки верните `60000` и перезапустите.

## Другие способы поднять качество без потери скорости (оценка)

| Идея | Что даёт | Цена |
|---|---|---|
| Снимок живого инцидента в фикстуру (REST `/v1/bots`, `/v1/board`, лог, позиции) одним скриптом | повторяемый вход в баг: GameTest или JUnit воспроизводит состояние доски и мира, а не пересказ | 1 скрипт + формат фикстуры; окупается на повторяющихся инцидентах |
| Воспроизведение инцидента из снимка мира в GameTest | проверка «до/после» на настоящем мире, а не на синтетической сцене | копия мира (≈85 МБ) и время прогона; делать только для тяжёлых багов |
| Живой сценарий как тест: записать REST-вызовы агента и проиграть их на тестовом сервере | ловит регрессии протокола и поведения духов | нужен стенд; полезно для `/v1/*`, не для рендера |
| Автоперенос правки: `hotswap` → прогон `scripts/test.sh unit --tests` → напоминание о тесте | не забыть тест после удачной живой правки | дисциплина агента; скрипт-обёртка цикла — следующий шаг |
| Дешёвый «дифф» поведения: до/после hotswap снять `/v1/board` и сравнить | видно эффект правки без чтения логов | 20 строк shell, полезно в цикле |

Главный выигрыш даёт связка «правка → живой результат → тест», а не отдельные инструменты: hotswap убирает
перезапуск, `eval` убирает сборку ради вопроса, брейкпоинт убирает догадки о состоянии, а замок делает это
безопасным для одного сервера и нескольких агентов.
