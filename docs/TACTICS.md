# Ядро тактики

Пакет `com.theminespirit.core.tactics`: чистая функция «обстановка → решение» без Minecraft. Адаптер раз в
`EVAL_INTERVAL_TICKS` (10, предварительно) или по событию «ударили» собирает `Situation` и вызывает
`TacticsEngine.step(Situation, TacticsMemory, nowTick)`. Ответ — `TacticalOutcome(decision, action, retreatMethod,
callHelp, state, mode, returnTo, trace, memory)`; `memory` адаптер передаёт в следующий вызов. Числа правил живут в
четырёх JSON `src/main/resources/data/theminespirit/tactics/`, код их не дублирует.

## Конвейер одного вызова

1. Режим: приказ стратега `Orders.mode` запоминается; таблица `modeTransitions` может временно сменить режим (устал,
   нет зоны, нет подопечного); решение этого вызова считается уже в новом режиме.
2. Факты (`Situation`, враги отсортированы по `(дистанция, тип, HP-доля, id)`, сверх `MAX_ENEMIES = 16` хвост
   сворачивается в запись «ещё n того же типа») → производные (`EnemyMetrics`, запас победы, способы отхода).
3. Жёсткие правила (`rules.json → hard`): первое подходящее по убыванию `priority` с `decision` решает; `exclude`
   вычёркивает варианты; вычеркнуто всё — `RETREAT` при наличии способа отхода, иначе `FIGHT`. Любое `RETREAT` (правило
   или оценка) без единого способа отхода подменяется правилами `then.noRoute` (первое подходящее, невычеркнутое):
    `no_route_fight_targeted` — FIGHT, если враг целится в духа; иначе `no_route_ignore` — IGNORE (враг вплотную
    обрабатывает `cornered_fight`). Крипер без оружия ближнего боя (`self.dps <= 1` — урон голой руки):
    `explosive_close_retreat` отводит на 5 блоках, `explosive_band_retreat` (приоритет 84) держит отход, пока дух в
    состоянии RETREATING и крипер ближе 8 блоков — полоса гистерезиса 5/8 данными против качки на границе 5/6 блоков.
    С мечом и без лука действует тактика «ударил–отошёл»: `explosive_strike_retreat` (приоритет 86) держит отход, пока
    с последнего удара духа (`time.sinceStrike`) прошло не больше 30 тиков (запал крипера) и крипер ближе 6 блоков, —
    отход по таймеру удара, а не по дистанции 5; без недавнего удара дух подходит счётом вплотную (≤3), чтобы ударить;
    `shoot_explosive` стреляет по взрывчатке от 3 блоков при луке.
4. Оценка `score(вариант) = Σ вес × фактор` для `FIGHT / RETREAT / IGNORE`, ничья — по `tieBreak`.
5. Гистерезис: прежнее решение держится `holdTicks` (кроме жёсткого правила, потери HP больше `hpDropRelease` за окно
   или вычёркивания) и получает `stickiness` к счёту после окна. Удерживается только решение, принятое оценкой
   (`score`, `hold`); решение жёсткого правила, единственного кандидата или «вычеркнуто всё» удержания не создаёт
   (`TacticsMemory.previousSource = RULE`): окно начинается с первого решения по оценке.
6. Действие (`actions`), способ отхода (`retreat`), состояние боя (`states`), `returnTo` (возврат к якорю после боя).

Порядок слоёв тика зафиксирован в `LayerOrder`: `POLICY > TACTICS > STRATEGY > IDLE`, прерванный слой возобновляется.
Политики безопасности и арбитраж тика — вне этого пакета.

## Схема JSON

Любая ошибка при загрузке — `IllegalStateException` вида «файл → путь: что не так. Проверьте: что сделать».
Неизвестные поля, дубли ключей и пустые таблицы запрещены. Загрузка: `TacticsConfig.loadDefault()` (один раз за
процесс) или `TacticsConfig.fromJson(enemies, weights, rules, modes)` из строк. Границы чисел держит
конструктор записи (`FactChecks.range`), парсер читает число без границ, а `ConfigNode.build` превращает отказ
конструктора в ошибку с путём в файле (`weights.json → scales.armorCap`); границы в одном месте.

| Файл | Содержимое |
|---|---|
| `enemies.json` | `{"enemies": [{type, hp, dps, speed, ranged, explosive, swims, flies, tier}]}`; ключ `minecraft:[a-z_]+`, обязателен `default` для неизвестного типа |
| `weights.json` | `scales` (масштабы факторов), `weights` (матрица фактор × вариант, полная), `tieBreak`, `stickiness`, `holdTicks`, `hpDropRelease` |
| `rules.json` | `hard`, `actions`, `modeTransitions`, `states`, `retreat` (`methods` + `callHelp` + `rally`); `id` правил уникальны на весь файл |
| `modes.json` | `returnTolerance` и на режим `{initiates, radiusBase, engageRadius, pursuitRadius, anchor, leash, returnToAnchor}` |

Правило: `{"id", "priority", "when": [атомы], "then": {...}}`. Атом: `{"fact", "op", "value"}`, `op` ∈
`< <= > >= == != in`; числа сравнивают все операторы, булевы факты — `==`/`!=`, перечисления — `==`, `!=`, `in`
(значение — список). `when` — конъюнкция, пустой список — «всегда».

- `hard.then`: `{"decision": "RETREAT"}`, `{"exclude": ["FIGHT"]}` или `{"noRoute": "FIGHT"}` (подмена RETREAT без пути;
  такие правила не участвуют в обычном проходе).
- `actions.then`: `{"action": "SHOOT"}`; решение выводится из действия, для каждого решения нужно замыкающее правило
  с пустым `when`.
- `modeTransitions`: `{id, from: [режимы], to, when}`; первое подходящее по порядку в файле.
- `states`: `{id, from: [состояния], to, decision?, when}`; `decision` — необязательное условие на решение.
- `retreat.methods`: `{id, method, requires, utility: {base, fact?, perUnit?}, bonus: [{when, add}]}`; полезность
  `base + perUnit × факт + бонусы`, в пределах 0..1; несколько строк одного способа допустимы (лучшая выигрывает);
  условия отхода не могут ссылаться на `env.escapeAvailability`.

## Факты

Единый реестр `FactName` с типом `NUM / BOOL / ENUM`; полный список и типы — в этом enum. Группы: `self.*` (HP-доля,
броня, урон, скорость, еда, блоки, дальний бой, ведро воды, союзники, лечилки), `enemy.*` (число, видимые, ближайший,
ближайший взрывной, суммарные HP и урон, быстрейший, флаги стреляет/взрывается/плавает/летает/целится в нас),
`env.*` (лава, обрыв, свет, ночь, дом, укрытие, вода, `escapeAvailability` = число доступных способов отхода),
`order.*` (режим, приказанный режим, инициирует ли, зона, `leashLeft`, `engageLeft`, подопечный, помощь), `time.*`
(`sinceHit`, `sinceStrike`, `sinceEnemySeen`, `inState`), `state.tactical`, `derived.winMargin`, `derived.speedRatio`.
`leashLeft = pursuit − расстояние от якоря до цели` (лучшая из целей), `engageLeft` аналогично для радиуса реакции;
«нет ограничения» — `Assessment.UNBOUNDED` (1000).

## Факторы

Каждый фактор — функция `Situation → [−1; 1]` (порядок enum `Factor` = порядок членов суммы); масштабы — `weights.json
→ scales`. `ownEhp = hp / (1 − min(armorCap, armorPerPoint × броня))`, `timeToKill = HP врагов / max(minDps, свой dps)`,
`timeToDie = ownEhp / max(minDps, Σ dps врагов)`.

| Фактор | Определение |
|---|---|
| `BIAS` | 1 |
| `WIN_MARGIN` | `clamp(log2(r) / winMarginDivisor)`, где `r = timeToDie / timeToKill`; врагов нет — 0 |
| `LOW_HP` | `clamp01((lowHpFloor − доля HP) / lowHpFloor)` |
| `ENEMY_PRESSURE` | `clamp01(1 − r)`: 0, пока дух убивает врагов быстрее, чем они его; та же величина `r`, что у `WIN_MARGIN`, — её проигрышная половина |
| `URGENCY` | `clamp01(1 − timeToDie / urgencyHorizon)` (`urgencyHorizon` = 10 с, `weights.json → scales`): абсолютное время до смерти; отличает «умру через секунду при равном перевесе» от «умру через минуту при том же перевесе» |
| `PROXIMITY` | `clamp01(1 − ближайший / proximityRange)` |
| `RANGED_EXPOSURE` | `clamp01(стрелков / rangedFull) × clamp01(1 − ближайший стрелок / rangedRange)` |
| `EXPLOSIVE_NEAR` | `clamp01(1 − ближайший взрывной / explosiveRange)` |
| `ALLY_SUPPORT`, `HEALING_AVAILABLE` | `clamp01(число / allyFull, healFull)` |
| `ESCAPE_ROUTE` | наибольшая полезность среди доступных способов отхода (0, если способов нет) |
| `TERRAIN_RISK` | максимум риска лавы `1 − лава/lavaRange` и обрыва `(высота − dropSafe)/dropRange` |
| `DARKNESS` | `max(1 − свет/15, ночью nightFloor)` |
| `HUNGER` | `clamp01((hungerThreshold − еда) / hungerThreshold)` |
| `PROTECT_URGENCY` | 1, если режим protect и подопечного бьют |
| `LEASH_PRESSURE` | `clamp01(1 − leashLeft / leashMargin)` при наличии врагов |

## Как добавить

- **Врага**: строка в `enemies.json` с ключом `minecraft:имя`; без неё враг оценивается профилем `default`.
- **Правило**: строка в нужной секции `rules.json` с новым `id` и приоритетом; добавить сценарий в
  `src/test/resources/tactics/scenarios.json`, который его вызывает (сторож `TacticsRuleCoverageGuardTests` краснеет
  на правиле без сценария).
- **Режим**: значение в `CombatMode`, запись в `modes.json`, перечисление в `FactName.enumValues`, правила смены режима.
- **Способ отхода**: значение в `RetreatMethod`, строка в `retreat.methods` с `requires`, полезностью и сценарием.
- **Вес или масштаб**: правка `weights.json`; после неё пройти `TacticsScenarioTests` — сценарии есть истина, веса
  подгоняются под них, а не наоборот.
- **Сценарий** (`scenarios.json`): `name`, `expect`, поля обстановки; сверх обязательного списка задания обязательно `why`
  (почему именно так; спорное решение геймдизайна помечается «СПОРНО» и ждёт согласования). Решение по счёту должно
  переживать сдвиг любого одного веса на ±10 % (`TacticsSensitivityTests`); если нет — сценарий помечается
  `"boundary": true` и `"pair"` (имя сценария с другой стороны границы). `memory.by` — `score` или `rule`: чем принято
  прежнее решение (удержание создаёт только `score`).

## Способы отхода

Полезность и условия — в `rules.json → retreat.methods`, числа взяты из п. 11 задания (tasks/19-tactics-core.md), ревью их приняло как есть:
`HOME` 1 − дистанция/160, `COVER` 0.4 (0.8 против стрелков), `KITE` 0.7, `WATER` 0.6 (ведро 0.55).
Отход не строит (решение владельца 18.10): баррикады и столба больше нет, дух только уходит — к дому или лагерю,
в укрытие, к воде, к союзнику или игроку, прочь. Блоки в инвентаре пути отхода не дают: зажатый дух дерётся
(`cornered_fight`, `no_route_fight_targeted`).
Найденной воды нет: ведро превращает WATER в `RetreatPlan.Pour` — вода ставится в клетку духа (тушит огонь и
гасит падение, MLG), пустое ведро возвращается в инвентарь; без ведра WATER-план вырождается в обычный отход
`HOME` (дом или лагерь), а если и точки нет — плана нет, как и раньше для способа без цели.
`RALLY` (полезность 0.2, но выбирается приоритетно, когда доступен) — сбор к ближайшему союзнику или игроку в радиусе
`retreat.rally.rallyRadius`; точка плана — сам союзник, а не точка «прочь от врага». Условие — факт
`order.helpAvailable`, который адаптер поднимает, когда рядом есть дух или не-спектатор-игрок в этом радиусе.
Низкая полезность не раздувает `ESCAPE_ROUTE`: сбор не делает отход привлекательнее там, где дух ещё может драться.
`AWAY` (бег прочь по открытой местности, полезность 0.2, ниже любого другого) добавлен ревью R6: условие — дух не медленнее
врага, враг дальше 3 блоков и нет стрелков (в спину бьют из лука) (ближе — `cornered_fight` обязан оставаться возможным).
Фактор `ESCAPE_ROUTE` — наибольшая полезность среди доступных способов (`RetreatOptions.bestUtility`, 0 при пустом
наборе): укрытие рядом толкает к отходу сильнее, чем голое поле. Масштаб `routesFull` в формуле больше не участвует.
Вес RETREAT (столбец `ESCAPE_ROUTE`) оставлен 0.3; возврат к 0.6 из спецификации проверен в игре (`TacticsWitchGameTests`) и отвергнут: при 0.6
два сценария с ведьмой («укрытие в 4, полное HP и меч», «укрытие в 4, есть лук») меняют решение FIGHT → RETREAT
(меч — COVER, лук — KITE), числа прогона: меч 0.463 против 0.444 при 0.3 и против 0.684 при 0.6, лук 0.463 против 0.414
и против 0.624. Сценарии помечены `boundary` с парой. Вместо роста ESCAPE_ROUTE усилен столбец низкого HP:
`LOW_HP.RETREAT` 2.5, `LOW_HP.FIGHT` −2.0 — при HP 30–40 % отход перевешивает атаку даже у сильного духа
(свойство `LowHpRetreatTests`, сценарий «HP 40 %, сильный меч, дом в 20»); так малый вес RETREAT 0.3 не
оставляет низкое HP на волю случая.

## Как читать trace

`TacticalOutcome.trace()` (`Trace.explain()` даёт текст): `rule` — id сработавшего жёсткого правила или `score` (по
оценке), `hold` (удержание прежнего решения), `excludingRules`, `totals` (счёт каждого варианта), `factors` (значение
фактора и вклад в каждый вариант), `actionRule`, `retreatRule`, `stateRule`, `modeRule`, `whyNotFight` — при
решении не `FIGHT`: вычеркнувшие бой правила, решившее правило или три фактора с наибольшим перевесом над боем.

## Границы

Не входят: REST-команда `set_combat_mode` (чеклист 22), командная тактика, политики безопасности. Вызов не делает ввода-вывода и не меняет аргументы; стоимость — O(16 факторов + правила + враги ≤ 16).

## Адаптер в игре

Пакет `core.tactics.adapter` (без Minecraft) и `neoforge.tactics` (тонкий слой над миром). `TacticsService` живёт в
`SpiritEntity`; порядок тика: политики → тактика → задача, пока политика владеет тиком, тактика только `pause()`
(оценок нет, отход и бой остановлены), после 10 тихих тиков `LayerArbiter` возвращает управление и сервис оценивает
обстановку принудительно. Тактика, которой есть что делать (бой, отход, возврат к посту), просит у арбитра слой TACTICS и
приостанавливает задачу.

- **Оценка**: `TacticsSchedule` — раз в `evalIntervalTicks` (10), по урону сразу (не чаще раза в 5 тиков), принудительно
  после политик и смены приказов. Вызов `TacticsEngine.step` один на оценку.
- **Факты**: `WorldFactCollector` — один `getEntitiesOfClass` радиуса `factRadius`, видимость лучом по клеткам
  (`LineOfSight`), окружение `EnvScanner` (вода, лава, обрыв, укрытие за стеной высотой 2) по решётке колонок радиуса 8
  ближние вперёд. Чтений блоков за оценку не больше `factChunkBudget` (64), прочитанное копится в `CellCache` (TTL 100
  тиков), поэтому вода и укрытие в 7 блоках находятся за несколько оценок; незагруженные клетки пропускаются, без врагов
  мир не читается. Дом — ближайшая точка памяти типа `base`.
- **Исполнение**: `CombatActuator` бьёт мечом из инвентаря (ATTACK_DAMAGE духа 1, лучший меч берётся в руку копией) и
  стреляет из лука; `RetreatPlanner` строит план отхода (бег к точке или ведро под себя), `RetreatExecutor` его исполняет,
  `RetreatCommitment` держит отход: бой прерывает бег, запасной AWAY уступает найденному лучшему способу.
- **Зов помощи**: при отходе и врагах не меньше `retreat.rally.callMinEnemies` дух кладёт `HelpCall` в координатор
  (в процессе, без сети) и пишет ближайшему игроку в радиусе `callRadius` «нужна помощь у x y z» не чаще
  `callIntervalTicks` (`HelpCallGate`). Координатор отвечает `HelpCallPolicy`: срочный приказ защиты получает
  ближайший дух в радиусе `helpRadius`, сам не атакованный и не зовущий сам; срочный приказ прерывает его задачу,
  а после снятия зова задача возобновляется.
- **Приказы**: `setCombatMode`, `setGuardZone`, `setWard` (будущая REST-команда `set_combat_mode` вызывает их); зона
  охраны — только явная, рабочая зона политик в приказы тактики не попадает.
- **Дом и лагерь**: отход `HOME` идёт к ближайшей из дома (`SpiritHome`) и лагеря похода (`Camp`,
  NBT `SpiritCamp`) через `SafePointChoice` — ничья за домом, нет обеих точек — «точки отхода нет»; скрипт
  `retreat` выбирает так же. Точка обороны поселения (`CoordinatorState.defendedPoint`) — ближайшая из дома
  и лагеря к духам. Быстрых укреплений в бою нет (решение владельца 18.10: «уберём полностью»); лагерь похода —
  только точка, его ставит игрок или стратег (`/spirit camp`, `set_camp`), блоков он не строит.
- **Состояние**: ключ NBT `SpiritTactics`, JSON версии 1 (`TacticsStateCodec`); испорченное состояние — ошибка в логе и
  `tactics().restoreFailure()`, дух начинает с режима по умолчанию DEFENSIVE.
- **Запись решения**: `TacticsTrace.format` пишется в лог уровня DEBUG при смене решения и доступна как
  `tactics().explain()`.
- **Журнал решений**: `adapter.json → journalCapacity` (32 записи) и `journalMaxPerSecond` (1) — кольцо последних
  записей на духа и предел их частоты. `DecisionJournal.offer(DecisionObservation)` сравнивает снимок прежней оценки
  (решение, режим, цель, приказ) с новой: нет ни одной разницы — записи нет; первая оценка духа только задаёт основу.
  Запись (`DecisionRecord`) несёт тик, имя и UUID духа, «было → стало» по сменившемуся полю, сработавшее правило или
  топ-3 фактора с весами (`DecisionReasons`, перевес выбранного варианта над ближайшим конкурентом) и ключевые факты
  (`DecisionFacts`: враги рядом и ближайший, здоровье, броня, оружие по `dps`/`rangedAmmo`). Строка `DecisionText.format`
  с префиксом `[tactics]` уходит в лог уровня INFO; те же записи отдаёт `GET /v1/spirits/{id}/decisions`
  (docs/API.md) и команда `/spirit decisions <дух>`.

## Откуда берётся угроза

Враждебные мобы сами берут духа целью: мод в `EntityJoinLevelEvent` добавляет в их `targetSelector` цель
`NearestAttackableTargetGoal<SpiritEntity>` с приоритетом уже имеющейся цели-игрока (`neoforge/MobTargetEvents`,
правило «кому добавлять» — белый список id в `core/tactics/SpiritTargets`). Бой поэтому начинается без игрока:
зомби у пшеницы сам приходит к духам. Нейтральные (эндермен, зомбифицированный пиглин), пиглины и иллагеры в
белом списке отсутствуют — у них своя логика агрессии. Крипер тоже целится в духа и подходит, чтобы взорваться:
на этом стоит тактика «ударь и беги». Выключатель — серверный конфиг `spirit.mobsTargetSpirits` (по умолчанию
`true`): при `false` мобы смотрят только на игроков, как в ванили.

Известные границы: плохо видны незагруженные чанки за 16 блоками; вода ищется в радиусе 8 блоков, и только
если её нет, WATER переходит на ведро — при найденной воде дух идёт к ней, а не выливает ведро под себя.

## Тактический интеллект

Один на поселение, внутри тика координатора (`neoforge/coordinator/SpiritCoordinator` владеет
`neoforge/intellect/SettlementIntellect`): отдельного цикла и реестра нет, снимок и бюджет — общие
с координатором. Раз в `DEMAND_INTERVAL_TICKS` (100) собирает `SettlementView` (запасы из инвентарей
духов и до 8 контейнеров рядом с домом — `StockReader`, вместе с лучшей едой склада; враги и дикая
живность одним запросом — `SettlementScanner`), зовёт `TacticalIntellect.decide` и применяет:
деятельности — push через `SpiritBrain.start`
(`CHOP` → `chop_tree`, `FARM` → `harvest_crop`, `MINE` → `mine_vein`, `REST` → `wait`,
`FORAGE` → `withdraw`/`hunt` (готовая еда склада дороже охоты, охота — только с оружием и по дичи вне
домашнего загона), `DEFEND` — пусто, обороной владеет координатор, `UNLOAD` → `unload` — разгрузка
инвентаря в контейнер), точечные брони целей — pull 31
внутри скриптов;
оценка сил — `StrengthDirector` (`FLEE`/`HEAL` — приказ отхода, `ARM` — `withdraw`+`equip` и затем бой,
`FIGHT` — приказ атаки, только если координатор приказа не дал). Очередь заданий стратегического
интеллекта (`StrategicQueue`) первой; REST-контракта очереди пока нет — очередь пуста
(«ждёт Стратега»). Экспедиция в шахту: команда 2–3, цель — точка под домом (H9, `locate_block` —
следующим этапом), приглашение игрока кнопками в чате (`/spirit invite <id> wait|go|join`,
радиус `SAY_HEARING_RADIUS` 64): `wait` продлевает на 60 с, `go` отправляет одних, `join` или
подошедший вплотную игрок — `follow` за ним, молчание 3 мин — идут сами (`mine_vein`).
Чужие задачи интеллект не трогает (как координатор 31 — только директивы): отменяет и
переназначает лишь задачи, выданные им самим (`TaskStarter` помнит выданное); провалившийся
скрипт не выдаётся тому же духу `FAIL_BACKOFF_TICKS` (200) — иначе провал-перезапуск забивает
лог и тик. Хозяйство (рубка, ферма, добыча, поход за оружием, экспедиция) — только у поселений
с домом: у одиноких духов нет ни складов, ни команды, их сцены чужих тестов не трогаем.
Движением в бою интеллект не командует вовсе: отходом владеют тактика духа и координатор
(посты и помощь), дублирующий приказ ломал их сцены (крипер-тест) — применяются только
`ARM` (сходить за оружием), `FIGHT` (если координатор приказа не дал) и деятельности.

Инвентарь духа — тоже хранилище: норма = базовый набор (`BaseKit`) плюс минимум текущей задачи (что план
заявил как нужное — инструмент, топливо, материал), всё сверх нормы — лишнее (`InventoryNorm`). Деятельность
`UNLOAD` («освободить инвентарь») есть всегда: её спрос растёт с долей занятых ячеек и долей лишнего, пустой
инвентарь даёт спрос 0. Кривые спроса и пороги удержания задачи — данные в горячей таблице `inventory_norm`
(`inventory/inventory_norm.json`, `/spirit tables`, `/reload`). Шахтёр (`mine_vein`, `dig_area`, спуск) и
рубка держат задачу до последней свободной ячейки, ферма и сбор бросают раньше — порог из той же таблицы
(`TaskRetention`).

## Организованный выход за границу

Решение владельца 15.10: за границу поселения/базы (шахта, отлов, поход, любая работа снаружи) выходят только
организованно — минимум `partyMin` духов или вместе с реальным игроком; один дух за границу не выходит.
Числа — данные `data/theminespirit/intellect/outside.json` (горячая таблица `outside`): `partyMin` (2),
`escortRadius`, `mineKit`. Граница поселения — радиус из `doors.json` (`NightLeash.settlementRadius`), второй
копии числа нет.

- **Допуск работы.** Деятельность, помеченная `Activity.external()` (сейчас `MINE`), попадает в раздачу
  `TacticalIntellect` только если `OutsideGate.admitExternal(party, playerEscort)` разрешает: группа рабочих
  не меньше `partyMin` или рядом реальный игрок (`playerEscort` считается адаптером по `escortRadius` от дома).
  Иначе деятельность не назначается, а причина уходит в `TacticalDecision.refusals` и в лог
  (`SettlementIntellect` печатает её при смене). Правило не трогает игроцкие `goto`: днём дух по прямой команде
  игрока за границу ходит (ночной поводок — отдельно, см. `NightLeash`).
- **Ночь.** Вечер и ночь (`eveningDayFraction` из `doors.json`, та же таблица, что у дверей) — жёсткая граница:
  `OutsideGate.admitExternal(party, playerEscort, evening)` отвергает внешнюю работу при любом составе и при
  игроке рядом, причина — «ночь: внешняя работа не назначается». Единственное исключение ночного поводка —
  следование за игроком (`follow`/`come_to_player`), а не работа рядом с ним. Вечером новый поход не
  начинается (`ExpeditionPlanner`): команда ночует в лагере/укрытии, уже вышедшая поводком домой не
  загоняется — `NightLeash.armedNext` взводит поводок только у тех, кого вечер застал внутри. Граница
  поселения — горизонтальный радиус дома, поэтому ствол шахты под домом остаётся территорией.
- **Напарник.** В походе ведущий (первый в команде `ExpeditionPlanner`) копает `mine_vein` и затем возвращается
  домой (`sequence(mine_vein, return_home)`), напарники идут рядом — `follow` за ведущим по UUID (радиус 3).
  Если напарник выбыл (смерть/отход), оставшиеся получают `return_home` и возвращаются на базу
  (`ExpeditionController.monitorMission`).
- **Набор перед спуском.** Перед диспетчем похода в шахту `ExpeditionController` собирает инвентарь команды и
  сверяет с `mineKit` (`DescentKit.missing`): кирка, факелы, еда. Нехватка — поход не начинается, причина
  («нужен набор: …») доступна как `ExpeditionController.refusal()`. Автоматический добор нехватки мелкими
  задачами доски пока не реализован.

## Передача вещей

Когда доска ставит крафт (кейсы набора инструментов `CRAFT_WOODEN_*` и `CRAFT_STONE_*`), `neoforge/board/TransferWatch` сравнивает ингредиенты
рецепта с инвентарём выбранного крафтера и зовёт чистый `core/social/TransferPlanner`. Излишек каждого духа
считает `InventoryNorm` (норма базового набора и нужды задачи не отдаются), источник — дух с наибольшим
излишком, при равенстве ближайший; дух за радиусом передачи не участвует, склад — запасной источник.
Пока передача не закрыта, крафт не выдаётся: в очереди стоят тикеты `TRANSFER_ITEM` с причиной
`transfer:<id крафта>`, излишек едет `deliver`-ом (или `withdraw`, если источник — склад). Журнал доски
пишет постановку (`modifiers`: получатель, предмет, количество, откуда), выдачу (`ASSIGNED`, держатель) и
итог (`DONE`/`FAILED`). Радиус и предел предметов — `board.json → intervals` (`transferRadiusBlocks`,
`transferMaxCount`), горячая перезагрузка работает как у остальных чисел доски.

## Оборона поселения

Слой единого тактического интеллекта, внутри того же тика координатора
(`SpiritCoordinator` владеет `neoforge/defense/DefenseService`, один на поселение):
отдельного цикла, снимка и реестра нет, интервал — `SNAPSHOT_INTERVAL_TICKS` (10) координатора.
На каждом тике: защитники из членов поселения (`DefenderReader`: позиция, доля здоровья, броня
не выше 20, лук, ближний урон в секунду, лечилка; выбывших и занятых задачей пропускает),
враги — `EnemyCollector` (один запрос, факты общие с интеллектом), заряженные криперы —
резолвом по id (`level.getEntity`, не скан), план — `DefensePlanner.plan` (сектора по силе
направлений, специализации лучник/мечник, цели по `priorities.json`, инстинкты поверх цели,
передача цели раненым), приказы — `DefenseDirectives` (пост без цели — `GUARD_AREA` на посту;
цель — `AGGRESSIVE` с навязанным id врага; отход/лечение и мечник против заряженного —
`PASSIVE` с точкой обороны). Применение — оверлеем поверх `CoordinatorDirectives` в том же
`applyPlan` (гистерезис по равенству приказа и навязанной цели): посты — `setGuardZone`,
цель — `setForcedTarget` (селектор конкретного моба не адресует, id едет отдельным полем),
зона держится и у атакующих. Помощь атакованному остаётся у `AssistPolicy` 31: приказ обороны
помощника не перезаписывает. Раз распределение взвешенное, при угроз уже защитников посты
схлопываются на угрожаемом секторе (квоты ядра) — равные сектора 31 действуют без угроз.
Прямое присутствие угрозы рядом с защитником — не бой: `AssistPolicy` зовёт неатакованного
(`threatsNear` не проверяется — передовые посты всегда в радиусе угроз), атакованный держится сам.
Бюджеты: один запрос сущностей и один план на пересборку; укрытия (`BlockerProbe`) — не больше
`BLOCK_BUDGET` (24) чтений блоков и только для `COVER_ENGAGE`; между пересборками мир не читается.
Ритм «ударил–отошёл» и дистанцию до крипера ведёт сам движок тактики
(`explosive_strike_retreat`, рефлекс `ExplosionAvoidance` выше приказов).
