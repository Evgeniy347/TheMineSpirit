# Стратегический интеллект духов

**Решение владельца 13.10.** Стратегический интеллект — настоящий ИИ (агент opencode или Sonnet через REST), один на всех
духов сразу, а не «стратег отдельного духа». Раз в 1–5 минут он смотрит на всё поселение: кто где, кто чем занят, запасы,
угрозы — и при необходимости корректирует: ставит задания конкретным духам в очередь, меняет цели. Простаивающих
духов заполняет не он, а тактический интеллект в моде (детерминированный, тоже один на всех — tasks/32,
`todo.md` → «Тактическое и стратегическое поведение»). Задания из очереди стратегического интеллекта исполняются
раньше расчёта тактического; угроза жизни вытесняет любое задание (политики > тактика > стратегия).

Ниже — устройство текущей программы (этап 0). Она пока работает по одному простаивающему духу за вызов модели —
переделка на «одно наблюдение всего поселения → одно решение на всех» — пункт todo.md.


Внешняя программа (`agents/strategist/`, Python 3 без зависимостей) раз в несколько минут решает, чем заняться простаивающему духу,
и ставит ему задачу по REST мода (`docs/API.md`). Мод LLM не вызывает; тактика (путь, бой, отход) детерминирована и живёт в моде.
Стратег меняет только цель и короткий план. Рабочий каталог `STRATEGIST_HOME` (по умолчанию `/opt/minecraft/strategist`) лежит вне
репозитория, содержит ники и в git не попадает.

## Схема цикла

1. `GET /v1/capabilities`, `GET /v1/bots` (контракт — объект `{"bots": [...]}`); неотправленные решения прошлого запуска досылаются с тем
   же `request_id`, если не старше `STRATEGIST_PENDING_TTL`, нет `PAUSE`, дух жив.
2. Для каждого `idle` духа (занятых и мёртвых не трогает никогда; при файле `PAUSE` новых задач нет):
   страж (пауза духа, лимиты вызовов модели и задач — до наблюдения) → `POST /v1/bots/{id}/observe` → промпт → мозг → разбор ответа → локальная проверка плана → `POST /v1/plan` →
   (при отказе проверки — один повтор с текстом ошибки) → страж → свежий `GET /v1/bots/{id}` → `POST /v1/bots/{id}/tasks`.
3. Отслеживание раз в 10 с: `GET /v1/tasks/{id}` до `succeeded|failed|cancelled`; `404` — исход `lost`; 30 мин — `DELETE`, исход `timeout`.

Ответ модели — один JSON: `{"reason","goal","plan"}` или `{"reason","skip":true}`. Отправляются только скрипты из `GET /v1/capabilities`
и из белого списка `agents/strategist/policy.json`, ≤ 32 узлов, ≤ 8 шагов в корне; `goto` не дальше `max_goto_distance` (256) блоков по
горизонтали от духа, `gather.block` — только природный блок из последнего наблюдения (`observed_block_params` + список `natural_blocks`
в `policy.json`: руды, камень, земля, песок, гравий, глина, брёвна, листва, растения; доски, стекло, кирпич и прочие постройки
игрока — отказ). Текст ответа склеивается из всех `text`-частей вывода opencode (одно сообщение может прийти несколькими частями).
Ошибка одного духа остальных не останавливает.

Для `mine_vein` и `gather` руды/камня локальная проверка требует кирку нужного уровня в инвентаре духа из наблюдения (поля
`inventory` и `held`). Уровни берутся не из таблицы стратега, а из структурного поля `requires` каталога
`GET /v1/capabilities`: у `mine_vein` уровень выбирает `ore` (`any`/`coal`/`quartz` — 1, `copper`/`iron`/`lapis` — 2,
`gold`/`redstone`/`diamond`/`emerald` — 3, `netherite` — 4), у `gather` — `block` (`stone` 1, `iron_ore` 2, `obsidian` 4;
блок вне таблицы кирки не требует). Значение `fallback` действует для параметра вне таблицы, `0` — требования нет.
Менять уровни — правкой каталога в моде, а не кода стратега. Без подходящей кирки
план отклоняется с текстом для модели; если в наблюдении нет ни списка предметов, ни предмета в руке, проверка даёт предупреждение,
а не отказ. Кирка и прочие инструменты накапливаются по шагам плана: после `acquire`/`craft`/`withdraw` предмет считается в инвентаре
следующих шагов, после `equip` — в руке; `sequence` и `fallback` передают накопленное дальше, `parallel` — нет. Поэтому
`acquire`/`withdraw` → `equip` → `mine_vein` — допустимая последовательность, а `mine_vein` первым шагом без кирки отклоняется.

Наблюдение в промпте показывает ресурсы компактно: предмет в руке (`held`), здоровье и сытость, задание доски
(`board_task`), ближайшие открытые (рядом есть воздух) позиции руд, камня и брёвен с расстоянием (`open_blocks`),
выпавшие предметы (`ground_items`) и содержимое сундуков (`container_items`) с пределами из
`data/theminespirit/observation/observation.json`, а также время суток (`time`, день/ночь и тик дня).
`open_blocks` мод отдаёт по возрастанию расстояния и не больше `maxOpenBlocks` записей, промпт оставляет 16 ближайших —
модель берёт координаты для `goto`, а не выдумывает их. Поля необязательные:
старое наблюдение без них разбирается и показывается как прежде, пустые новые поля в промпт не попадают. Промпт объясняет шкалу
сытости (`food` от 0 до 1, где `1.0` — сыт) и правило осторожности: при низком здоровье или ночью модель выбирает короткие
безопасные планы рядом с домом, а не бой и глубокую шахту.

Остановка (`SIGTERM`/`SIGINT`, `strategist.sh stop`): обработчик поднимает флаги и шлёт `SIGKILL` группе текущего вызова мозга —
без `wait()`, который в обработчике мог бы ждать сам себя. Вызов прерывается сразу (`BrainStopped`), а не через
`STRATEGIST_BRAIN_TIMEOUT`: цикл заканчивается, после прерванного вызова ничего не отправляется, в журнале нет `brain_failure`
(остановка — не сбой модели: backoff не растёт), процесс выходит с кодом 0. Опрос задач идёт только между вызовами модели:
вокруг вызова нет ни одного `GET /v1/tasks/{id}` (сторож — `tests/test_stop.py`).

`…PROBE_TIMEOUT`, `…OPENCODE_BIN`) — в `agents/strategist/config.py`.

## Режимы и этапы

- `dry` (по умолчанию): наблюдения, модель, проверки и `POST /v1/plan` идут как обычно; вместо `POST tasks` в журнал пишется `posted`
  с `dry:true, outcome:"would_post"`. Записи dry видны модели в «Недавних решениях» (она знает, что уже решила) и **не** тратят лимит
  задач в час: он считается только по настоящим `POST tasks`.
- `live`: задачи ставятся. `405` или `404` при живом духе (маршрута нет) — один `alert` и `dry` до конца запуска; `404` при исчезнувшем духе —
  запись `rejected`, режим не меняется.
- Этапы: 0 — фейковый REST и `smoke`; 1 — `dry` против живого сервера, когда опубликован чеклист 14; 2 — `live` на одном духе, затем
  на всех, первые 10 решений просматривает человек, когда опубликован чеклист 15. Публикация и `live` — только по согласованию с пользователем.

## Защита от спама и зацикливания

≤ 10 задач на духа в час и пауза ≥ 60 с; ≤ 30 вызовов модели в час; тот же план после `failed/lost/timeout` — кулдаун 30 мин;
отпечаток плана — точный SHA-256 нормализованного плана (скрипт и нечисловые ключевые параметры): смена только `count` или
радиуса не создаёт новый план и не обходит кулдаун; 3 провала подряд — пауза духа 5 мин и `alert`; отмена человеком
(`cancelled`) провалом не считается — ни кулдауна, ни паузы, серию провалов не продолжает; `hash` наблюдения не изменился с прошлого решения — модель не вызывается; в dry повтор
того же плана (наблюдение изменилось, но модель решила то же) помечается `duplicate:true` и не считается новым решением, а настоящая
задача сбрасывает эту память; провайдер
недоступен (сбой провайдера или сетевой сбой: нет соединения, недоступность конечной точки — шаблоны в `brain.py` теми же, что в
`scripts/opencode-task.sh`, их равенство держит тест) — интервал ×2 до 30 мин и проба «ответь OK» вместо полного промпта; запросы к REST ≤ 5/с, `429` — ждать `Retry-After`;
дух стал `busy` до отправки — решение отброшено; `request_id` детерминирован (`uuid5` от духа, цикла и отпечатка плана).

## Журнал и состояние

`STRATEGIST_HOME/journal.jsonl`: строка на событие, поля `schema, ts, cycle, event, bot, model, prompt_sha, reason, plan, request_id,
task_id, outcome`. События: `cycle_start, bot_skipped, observed, decision, rejected, posted, task_state, task_done, brain_failure, alert`.
Ответ модели усечён до 4 КиБ; ротация 10 МиБ × 5 файлов. При отказе разбора ответа модели сырой вывод opencode и время ответа
сохраняются в `STRATEGIST_HOME/runs/failed-*` для разбора. Примеры: `grep '"event":"rejected"' journal.jsonl | tail`, `scripts/strategist.sh status`.
`state.json` (активные и неотправленные задачи, счётчики стража) пишется атомарно; повреждённый файл переименовывается в
`state.json.corrupt-<время>` с `alert`, молчаливого сброса нет. `strategist.log` — вывод процесса.

## Мозг: сменить модель, подключить Sonnet

`opencode`: `opencode run` в песочнице `STRATEGIST_HOME/sandbox` без флагов обхода разрешений. Общий шаблон `"*": "ask"` стоит
первым ключом: `deny` (в том числе общий) убирает `read/edit/bash` из набора инструментов — бесплатный тариф отвечает `403`
(«free tier can only be used from within OpenCode»), а модель не может даже попытаться выполнить `ls`. Поэтому нужные
инструменты `ask` (в неинтерактивном запуске запрос отклоняется автоматически), остальные — `deny`. Файл проверяется при
каждом вызове, а при старте `opencode debug agent strategist` даёт итоговые права: `read/edit/bash` включены, для каждого
включённого инструмента последнее общее правило обязано быть ask/deny, иначе отказ запуска (код 4).
Переменные `OPENCODE_PERMISSION/CONFIG/CONFIG_CONTENT/CONFIG_DIR` из окружения мозга убираются. Выполненный инструмент —
`alert sandbox_breach`, файл `PAUSE`, остановка агента (код 5). Каталог данных подпроцесса (`XDG_DATA_HOME`) — свой,
`STRATEGIST_HOME/opencode-data`: сессии с полным промптом не копятся в общем `~/.local/share/opencode`. Вход в аккаунт
держится симлинком на глобальный `auth.json`, а подписка `opencode-go` — строками `account`/`account_state` в своём
`opencode.db`: из общего `opencode.db` переносятся только схема, миграции и эти строки учётки, без сессий и сообщений;
ключи не логируются. Так изоляция данных не ломает ни бесплатный тариф, ни модели `opencode-go`. Модель меняется переменной,
правка кода не нужна; рабочие модели — в `docs/EXECUTOR-MODELS.md`.
`command`: `STRATEGIST_BRAIN=command STRATEGIST_BRAIN_COMMAND='/путь/к/скрипту'`. Команда читает со stdin JSON `{"system","user","model"}`
и печатает ответ в stdout; код выхода 75 — «модель недоступна» (включает интервал ×2), любой другой ненулевой — ошибка мозга. Так
подключается Sonnet 5.5.

## Белый список скриптов (чеклист 38Б)

`allowed_scripts` в `agents/strategist/policy.json`: базовые `goto`, `scan`, `collect_drops`, `chop_tree`, `mine_vein`,
`gather`, `till`, `plant_crop`, `harvest_crop`, `bone_meal`, `wait` и инструментальные `acquire`, `craft`, `equip`,
`withdraw`. Скрипт должен быть и в `GET /v1/capabilities`. Проверка `test_plan_check.py` держит список и сценарии;
при осознанной смене поправьте тест.

- `acquire` — получить предмет с нуля: мод сам строит цепочку (рубка → доски → верстак → кирка → камень); `item` —
  id предмета, `count` — 1..256.
- `craft` — скрафтить из материалов, которые уже есть в инвентаре; `item`, `count`, `radius`.
- `equip` — надеть предмет из инвентаря; `item` — точный id или шаблон (`*_pickaxe`), как в `IdFilter` мода.
- `withdraw` — взять из контейнера рядом; `container` (`nearest` или `"x,y,z"`), `item`, `count`, `radius`.

Локальная проверка плана (`plan_check.py`) для всех четырёх требует обязательные поля и пределы `count` из каталога и
проверяет `item` как id предмета: символы `a-z 0-9 _ : . / -`, не больше одного `:`, непустые namespace и path до и после
него; подстановка `*` разрешена только `equip`. Пустая строка, пробелы, заглавные буквы, кириллица и шаблон в
`acquire`/`craft`/`withdraw` отклоняются до отправки с текстом для модели.

Порядок «сначала инструмент» закреплён в `prompt/system.md` и сценариях `tests/scenarios/45..48`, а накопление инструмента
по шагам плана — сценариями `50..51`: пустой инвентарь → план начинается с `acquire` кирки, а не с `mine_vein`; кирка есть →
`mine_vein` допустим; сундук рядом → `withdraw`; инструмент в инвентаре не в руке → `equip`; `acquire`/`withdraw` → `equip` →
`mine_vein` проходит, потому что кирка накоплена с предыдущего шага.

## Природные блоки: что духу можно добывать

`natural_blocks` в `policy.json` — группы имён блоков без префикса `minecraft:` (руды, камень, земля, сыпучие, лёд, брёвна, листва,
растения, терракота, прочее природное). Правило работает вместе с `observed_block_params`: блок должен быть и в последнем наблюдении,
и в этом списке. Постройки игрока (доски, стекло, кирпич, двери, кровати, сундуки) в наблюдение попадают, но в список не входят,
поэтому `gather.block` с ними — отказ до отправки с текстом для модели. Менять состав — менять и тест
`test_policy_NaturalBlocks_CoverNaturalGroupsAndExcludePlayerMade`: он сторожит обе стороны правила.

### Проверка песочницы после обновления opencode

`scripts/strategist.sh sandbox-check` просит модель выполнить `ls` и проверяет, что в выводе `opencode` есть `tool_use`
с `status:"error"` (песочница отклонила вызов) и нет выполнения. Код 0 — отказ подтверждён, 1 — инструмент выполнился
или модель не попыталась его вызвать, 2 — проверка неприменима (`STRATEGIST_BRAIN=command`) или неверная конфигурация.
Запускать после каждого обновления opencode; результат и версию записывать сюда. Проверенная версия — **opencode 1.19.3**
(18.10, ПК): ручной прогон `opencode run` с моделью `opencode/big-pickle` в этой песочнице дал `tool_use` `bash` со
`status:"error"` («The user rejected permission to use this specific tool call.»), выполнения не было.

## Команды

`scripts/strategist.sh start|stop|status|pause|resume|once|sandbox-check|smoke [модель]|logs [N]` (tmux-сессия `mc-strategist`, второй экземпляр
отказывается). `strategist.py … --fixtures agents/strategist/tests/fixtures` поднимает фейковый REST из записанных наблюдений. Тесты:
`scripts/testing/check-strategist.sh` (все строки `OK`) или `cd agents/strategist && python3 -m unittest discover -s tests -t .`.
Сценарии (`tests/scenarios/*.json`) и свойство случайных сценариев идут **без сети**: один и тот же фейковый REST зовётся
внутри процесса (`InProcessClient` вместо сокета), поэтому оба прогона укладываются в предел 10 с, записанный в самих
тестах (чеклист 22, п. 11). Сам фейк по HTTP проверяется `tests/test_fake_rest.py`, чтобы сценарии не зеленели вхолостую.

`smoke` не входит в проверку: он пишет `STRATEGIST_HOME/smoke-<время>.md` (доли валидных ответов, время, колонка для оценки глазами).
