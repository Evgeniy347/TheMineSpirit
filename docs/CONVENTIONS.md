# Соглашения кода

## Комментарии: код объясняет себя, тест защищает поведение

В production-коде (`src/main/java/**`) комментариев минимум.

Запрещено:

- Javadoc на членах класса;
- комментарии, пересказывающие код;
- разделители (`// ── Блоки ──────`);
- закомментированный код;
- `TODO` / `FIXME` / `HACK` — вместо них заводится задача.

Куда идёт объяснение вместо комментария:

1. **Переименование.** Если комментарий объясняет, ЧТО это за метод, поле или константа, — имя неверное.
   Выноси выражение в именованную переменную или константу, пока строка не читается как фраза.
2. **Тест.** Если комментарий объясняет, ПОЧЕМУ (баг, от которого защищает код, ограничение Minecraft,
   замер), — причина уходит в тест, который краснеет при нарушении. Имя теста несёт поведение,
   сообщение assertion — причину.

Допустимы короткие комментарии там, где код и тест причину не объясняют: ограничение Minecraft/NeoForge
или сторонней библиотеки, обязательный внешний контракт, обоснование подавления предупреждения, лицензия.

При любой правке production-метода пересматриваются все комментарии внутри него. Удаляя комментарий
с объяснением «почему», убедись, что его смысл сохранился: тест уже есть, ты написал его в том же коммите,
или новое имя кода несёт это «почему». Массово чистить нетронутые методы без отдельной причины не нужно.

В тестах комментарии разрешены (`// Arrange` / `// Act` / `// Assert`, пояснение нетривиальной подготовки),
но то, что нужно для разбора падения, — в имени теста и в сообщении assertion.

## Структура: класс делает одно дело

Лимита строк нет, есть симптомы. Любой из них означает, что класс нужно разделить до изменения:

- в классе две и более независимых секций с разными существительными;
- поля распадаются на непересекающиеся группы, которые используют разные методы;
- метод принимает 3+ boolean-параметра, описывающих, КАКОЙ объект он получил, — это флаги вместо
  полиморфизма: нужен тип, стратегия или enum;
- метод принимает 8+ параметров — нужен объект-результат или объект-параметр;
- одна и та же лестница `if (x instanceof A) … else if (x instanceof B)` больше чем в одном методе;
- две почти одинаковые семьи методов — общее выносится, но сначала сравни их построчно;
- одна и та же последовательность настройки объекта повторяется трижды — это конструктор или builder;
- метод работает с другим объектом, чем говорит его имя.

Следствия:

- Один метод — одна работа, ориентир ~40 строк.
- Добавлять фичу в класс, где уже есть отдельная зона для другой фичи, запрещено: создай класс.
- Проверка типа (`instanceof`, сравнение с `Blocks.X`/`EntityType.X`) живёт в ОДНОМ месте на слой:
  тип решается один раз и превращается в данные или в вызов метода, дальше код не переспрашивает.
  Порядок устранения лестницы: спросить сам объект (метод) → общий интерфейс → новый интерфейс →
  реестр обработчиков → enum возможностей, названных по возможности, а не по типу.
- По умолчанию — конкретные классы. Интерфейс вводится только на внешней или платформенной границе.
- Не добавляй `Function`/`Supplier`/`Runnable` в production API только ради подмены в тестах.

## Быстрый путь: логика без игры живёт в `core`

- Пакет `com.theminespirit.core` не импортирует `net.minecraft`, `net.neoforged`, `com.mojang`.
  Его проверяет чистый JUnit за секунды, без запуска игры. Сторож — `CoreIsolationTests`.
- Новый класс, которому не нужен мир, идёт в `core` вместе с тестами в том же коммите.
- Код, которому нужна игра, — тонкий адаптер: собирает данные из мира, вызывает чистую функцию
  из `core`, применяет результат. Решение «что делать» — чистая функция, а не состояние с кэшем.

## Строгость сборки

- Компиляция: `-Xlint:all -Werror` (см. `build.gradle`). Предупреждение — ошибка сборки.
  Подавление (`@SuppressWarnings`) — только точечно и с причиной рядом.
- Версии зависимостей — только в `gradle.properties`, не по месту в `build.gradle`.
  Менять версии — решение пользователя (см. AGENTS.md).
- Файлы в `src/generated/` создаются datagen (`./gradlew runData`) и руками не правятся.
- Сторонняя библиотека мода (не Minecraft) объявляется трижды: `implementation` (компиляция),
  `additionalRuntimeClasspath` (dev-запуски и GameTest-сервер) и `jarJar` (упаковка в jar мода).
  Без `additionalRuntimeClasspath` dev-запуск падает с `NoClassDefFoundError`, без `jarJar` — сервер игрока.
  Образец — Jackson в `build.gradle`.

## Производительность

Код мода исполняется в серверном тике (20 раз в секунду) и на мирах с тысячами чанков и сущностей.

- Цикл по сущностям/блокам внутри цикла по сущностям/блокам, пересборка коллекции целиком на каждом шаге,
  повторный поиск по миру там, где хватит одного прохода, — дефект, а не стиль.
- Горячие пути: обработчики тика, событий блоков и сущностей, генерация мира. Правка там сопровождается
  тестом на масштаб, который считает операции, а не миллисекунды.
- Нашёл медленное в своей зоне — чини в том же заходе. Не в своей — одна строка в отчёте: что, сколько,
  чем измерено.

## Ошибки

- Тихий fallback — авария, а не защита: не глотай исключения и не подставляй «значение по умолчанию»
  молча. Либо явная ошибка, либо запись в лог с причиной.
- Сообщение об ошибке называет, что сломалось и что проверить.

## Файлы и кодировки

- Все исходники — UTF-8 без BOM. `*.sh` — LF, `*.bat` — CRLF и только ASCII (см. `.gitattributes`).
- После `sed -i` проверь `git diff --stat`: если изменилось больше строк, чем ты правил, уехали
  переводы строк — верни их.
- Новый файл: сначала проверь, что имя не занято, — запись поверх существующего файла проходит молча.

## Временные файлы

| Каталог от корня | Назначение |
|---|---|
| `temp-scripts/` | одноразовые скрипты, пробы |
| `TestResults/` | отчёты тестов, логи прогонов, дампы |

Оба каталога игнорируются Git; при отсутствии — создать. Не добавлять их содержимое через `git add -f`.
Не создавать временные файлы вне репозитория и рядом с исходниками. Удалять только то, что создал сам,
проверив точный путь. Постоянные скрипты — исходники проекта: живут в `scripts/` и описаны в README.

Логи сервера могут содержать ники и IP игроков: не публиковать и не коммитить их.
