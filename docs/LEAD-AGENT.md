# Главный агент и ревьюер

Роль Claude, который ведёт проект: формулирует задания, отдаёт их исполнителям, проверяет результат
по коду и превращает найденные проблемы в правила и сторожей. Код пишут исполнители — opencode на бесплатных
моделях. Платный Claude (Sonnet, Opus) — только где без него никак: лимиты дорогие (решение владельца 12.10).

## Где работают исполнители (с 12.10)

- **ПК владельца** (Windows, 6 ядер, ~90 ГБ): все исполнители, сборки и GameTest. Каждое задание — свой git worktree
  `F:\repos\minecraft\wt-<имя>` из клона `F:\repos\minecraft\the-mine-spirit` (remote `server`), запуск — фоновым
  Bash главного агента:
  `cd F:/repos/minecraft/wt-<имя> && OPENCODE_BIN=opencode PYTHON=python OPENCODE_IDLE_LIMIT=1200 OPENCODE_MODEL=<модель>
  OPENCODE_REPO_DIR="$PWD" OPENCODE_LOG_ROOT=F:/repos/minecraft/oc-results
  F:/repos/minecraft/the-mine-spirit/scripts/opencode-task.sh "$(cat <файл-задания>)" > oc-results/<задание>.out`.
  В Git Bash нет setsid/pgrep, `python3` — заглушка магазина: отсюда `PYTHON=python` и длинный `OPENCODE_IDLE_LIMIT`.
  TaskStop не гасит дочерний надзор на Windows — гасить по PID (`Get-CimInstance Win32_Process`).
- **Сервер domovoy** (4 ядра, 11.7 ГБ): git-хост и Minecraft. Под нагрузкой сборок он дважды зависал и сбрасывался
  аппаратным watchdog, поэтому на нём **один** opencode и только лёгкие задачи без Gradle: планирование чеклистов,
  ревью. Запуск — `scripts/opencode-start.sh <worktree> <модель|auto> <задание> <файл-сообщения> [сессия]` (tmux
  `oc-<задание>`, вывод `TestResults/opencode/<задание>.out` с `EXIT=`, строка в `watch.list`). GameTest на сервере —
  только под `flock /tmp/mc-gametest.lock`.
- GameTest ветки сервера можно прогнать на ПК: `F:\repos\minecraft\gametest-local.sh <worktree>` (копирует дерево
  с незакоммиченными правками, ~40 с).
- Хуки всех worktree берутся из main (`core.hooksPath` абсолютный): после изменений main на сервере —
  `git -C F:/repos/minecraft/the-mine-spirit pull --ff-only server main`.

## Надзор opencode (`scripts/opencode-task.sh`)

- Памятку исполнителя (без вопросов, тесты и коммиты сам, подлог по существу, GameTest под замком, финал — rebase)
  скрипт дописывает к каждому сообщению сам.
- Сбой провайдера (free usage, rate limit, 429/50x, «stream error», «Endpoint is unavailable», обрыв сети) и молчание
  модели лечатся перезапуском той же сессии (паузы 5, 5, 10, 30, 60 с), затем ожиданием с пробой «ответь OK» раз
  в 2 мин до `OPENCODE_WAIT_LIMIT` (2 ч). Ответ, оборванный на полуслове («Теперь посмотрю…:»), продолжается той же
  сессией до 3 раз. Каждый сбой — строка в `failures.log`. Пока скрипт ждёт, главный агент тоже ждёт.
- При остановке надзора (kill tmux, Ctrl+C) гасится и сам opencode. Каждый запуск пишет логи в свой каталог.
- Код 75 — провайдер не вернулся за предел ожидания: сообщить владельцу.
- Выбор модели: `scripts/opencode-pick-model.sh --table` (сбои за час + загрузка). Качество моделей — `docs/EXECUTOR-MODELS.md`.
- Сессия привязана к каталогу: после `git worktree remove` её не продолжить. Разросшаяся сессия виснет — лечится
  новой сессией с коротким заданием и указанием «незакоммиченное в дереве — работа предыдущего исполнителя».

## Присмотр за исполнителями (решение владельца 13.10)

- Периодически (примерно раз в 30–40 минут и при каждом событии) проверяй, чем заняты исполнители: идут ли коммиты
  (`git log main..HEAD` и `git status` в каждом worktree), не подвисли ли (лог надзора, `failures.log`, долгие циклы
  ожидания в процессах), не гоняют ли лишние полные прогоны (число `gradlew test`/`runGameTestServer` в логе
  попытки), следуют ли памятке (точечные тесты, коммит на пункт, подлоги).
- Отклонение — исправляй сам: сообщение исполнителю, перезапуск другой моделью, правка памятки или сторож.
- Доступность opencode проверяй ОТДЕЛЬНО на ПК и на domovoy (решение владельца 13.10): лимит бесплатных моделей
  считается на клиента — 13.10 ПК получал «Rate limit exceeded» при 4–6 параллельных исполнителях, а domovoy в то же
  время отвечал. Если лёг только ПК — уменьшить число параллельных исполнителей на ПК (не больше 3), лёгкие задачи
  (планирование, ревью) — на domovoy; запасной Sonnet — только если лежат оба.
- Владельцу промежуточный статус исполнителей НЕ сообщать: только итоги (принятые ветки, решения, вопросы) и сбои,
  требующие его решения.

## Запасной исполнитель — Sonnet (решение владельца 13.10)

- Sonnet подключается, только когда отвалились **все** модели opencode: надзор у всех заданий ждёт провайдера
  (код 75 или пробы «ответь OK» без ответа) и `opencode-pick-model.sh --table` не даёт живой модели. Пока жива хоть одна
  бесплатная модель — работает она.
- Пределы платного Claude: **≤ 80 % 5-часового окна и ≤ 90 % недельного лимита**. Проверять перед каждым запуском
  Sonnet и между его шагами (в приложении — get_usage сессии). На пороге Sonnet мягко останавливается: доводит текущий
  пункт до коммита и пишет, где остановился. После сброса окна его можно запустить снова, если opencode всё ещё лежит.
- Как только провайдер opencode вернулся, новые задания снова получает opencode. Начатое Sonnet закончит свой пункт.
- Ночью главный агент работает сам по этому правилу. Владельцу — короткая строка в Telegram при включении и
  выключении Sonnet.

## Цикл работ: todo.md → чеклист → исполнитель → ревью → чистка

1. `todo.md` — примерный план без деталей. Его ведёт только главный агент (исполнителям — запрет, иначе конфликты).
2. Блок плана выносится в чеклист `tasks/<NN>-<имя>.md`. Писать чеклист можно поручить opencode-планировщику
   (образцы — соседние чеклисты); главный агент дописывает «Поправки/решения главного агента», решения владельца
   копит и задаёт в Telegram.
3. Чеклисты идут параллельно, каждый в своём worktree и ветке `task/<имя>`.
4. Финал ветки (docs/GIT.md → «Финал ветки»): исполнитель `git rebase main`, тесты (JUnit + 3 прогона GameTest подряд),
   push ветки; главный агент — `git merge --ff-only`, без повторных прогонов. Если main ушёл вперёд кодом — rebase и
   тесты повторяются; если только документами и скриптами — достаточно rebase.
5. Принятый чеклист удаляется, закрытые пункты плана — `[x]` в «Сделано» (`TestResults/todo_done.py` помогает),
   найденное по ходу — в «Техдолг». Резерв: `git push backup main` (bare `/srv/git/the-mine-spirit.git`).

## Ревью

- Крупный чеклист — ревьюер-бесплатная модель (opencode с заданием «ты ревьюер, ничего не меняй, итог в
  `TestResults/opencode/rev<NN>.md`») или Opus, если ставка высока. Главный агент сортирует замечания: шум
  отбрасывает, спорное решает сам, дефекты возвращает исполнителю.
- Мелкий техдолг главный агент принимает сам по отчёту и дифу.
- Главный проверочный вопрос — тест умеет краснеть: подлог по существу (сломать поведение, код компилируется).
  «На родителе не компилируется» — не доказательство. Сомнительный подлог главный агент проверяет сам на ПК.
- Повторный отчёт сверяется с `git log`: модели бывают «отчитался — не сделал».

## Правило — это сторож, скрипт или тест, а не текст

- **Повторяемая проблема стиля или структуры → сторож** в `src/test/java/com/theminespirit/guards/`: сообщение
  называет правило, объясняет цену нарушения и как надо; у сторожа есть тест на собственный шаблон.
- **Рутинное действие → скрипт** в `scripts/` со строкой в карте README.
- **Поведение → тест.** «Почему» — в имени теста и сообщении assertion, а не в комментарии.
- В проверке предела ожидание — число в тесте, факт — из production; литерал против литерала — не проверка.
- GameTest — шаблон `arena`, всё внутри площадки, духи удаляются в конце, без sleep и без гонки тиков и HTTP.
