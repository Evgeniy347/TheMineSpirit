## Стабилизация этапа (владелец 11.11)

Ориентиры главному агенту, исключения — с причиной владельцу:
- Пока этап нестабилен в живом мире, новые механики не запускаются; задачи — из приёмки живого мира.
- Каждый присмотр смотрит живые инварианты, а не только статусы: версия мода = main, тик, новые столбы
  в зоне, смерти от падения, простой духов, повтор провала по одной причине.
- Не более одного исполнителя на связанный код (навигация/расчистка/аренда) одновременно.
- Последствия ошибок в мире (столбы, мосты) можно убрать разово скриптом по журналу блоков — только
  блоки духов вне плана, со снимком мира и согласия владельца.

## Слияние и выкладка

- Отчёт исполнителя + `git log main..ветка`: сторожа не ослаблены, тесты не отключены. Слияние на ПК в main
  (хук гоняет unit); конфликт — по смыслу сам или исполнителю той ветки.
- Выкладка (`scripts/publish.sh` — только сборка `assemble`, без тестов): `git push server main:lead/main`, на
  сервере `merge --ff-only lead/main`, `push backup main`, `publish.sh -y` из main (повтор при сбое). Скрипт сам
  раскладывает скрипты и конфиги сервера из `server/`, ставит jar, обновляет пак клиента, страницу «Сервер» и тег;
  вручную пак и файлы сервера не трогать. Живая сборка — `--temp`
  из дерева задачи, возврат — `publish.sh -y` из main. После рестарта — `difficulty peaceful` и
  `forceload add -270 -587 -70 -387`, затем проверить лог (`ERROR`, `[plot]`, `[clear]`) и духов по REST.
- До установки `publish.sh` проверяет jar по содержимому: `META-INF/neoforge.mods.toml` есть, не пуст (0 байт =
  «Missing ModLoader») и содержит `modId`, классов больше 1000; иначе — ОШИБКА и выход без остановки сервера, установки
  и пака. Ту же проверку на сборке делает `:mod:verifyModJar`; поведение держит `scripts/testing/check-publish.sh`.
- После слияния — уборка: worktree и ветка (`git branch -d`), чужие ветки владельца (`owner/*`, `wt-owner`) не
  трогать.

## Снимки мира

- Снимок без остановки сервера: на сервере `/opt/minecraft/server/scripts/world-snapshot.sh [метка]`
  (исходник — `server/scripts/world-snapshot.sh` репозитория мода, `publish.sh` раскладывает его на сервер).
  Архив `world-<дата_время>[-метка].tar.zst` (≈85 МБ, 2 с) ложится в `/opt/minecraft/backups/world/`;
  скрипт сам делает `save-off` → `save-all flush` → архив → `save-on`. Мир в git не хранится.
- Каждую команду сохранения консоль подтверждает строкой в `latest.log`; молчащая консоль — отказ с причиной
  («консоль не читает stdin» → перезапуск сервера), а не «сервер не подтвердил». `save-off` без подтверждённого
  `save-on` не остаётся, готовый архив не выбрасывается. Занятый снимком замок публикация ждёт (900 с), cron
  пропускает с кодом 75 и пишет, кто держит.
- Cron `domovoy` снимает архив каждые 10 минут, лог — `/opt/minecraft/logs/world-snapshot.log`. Ротация: всё за 24 ч,
  дальше по одному в час на 7 дней, дальше по одному в день на 30 дней; архивы с меткой не удаляются,
  при нехватке места (меньше 10 ГБ) удаляются самые старые.
- Откат: `/opt/minecraft/server/scripts/world-restore.sh [-y] <архив>` (без имени — список). Скрипт
  сохраняет текущий мир архивом `before-restore`, штатно останавливает сервер, разворачивает архив,
  запускает сервер и возвращает `difficulty peaceful` + `forceload -270 -587 -70 -387`. При сбое
  запуска прежний мир возвращается на место.
- Правило: перед рискованным экспериментом — снимок с меткой (`world-snapshot.sh before-<что>`).
  Испортить мир не страшно: откат занимает около минуты.

## Сироты и зомби

- Обход дерева `opencode run` видит только живую цепочку исполнителя. Прогон, у которого родитель
  умер, в это дерево не входит: счётчик «opencode run = число живых» его пропускает.
- Смотреть: `bash scripts/lead/orphans-win.sh` (или через `res-pc.ps1`/`oc-watch.sh`). Детектор сам
  показывает сирот `scripts/test.sh`, `gradlew`, `java`: PID, CPU за интервал, возраст, worktree из
  командной строки, причину и команду. Он **никого не убивает** — гасит главный агент, по PID,
  убедившись, что прогон чужой и ненужный.
- Признак настоящей поломки — не просто «родитель умер» (фоновый прогон так и выглядит), а **CPU
  около ядра** у такого процесса: ожидание выродилось в busy-loop. `test.sh` ждёт встроенным
  `read -t` (pause_tick), поэтому тиканье не крутит процессор; тест `wait-cpu` проверяет, что надзор
  не порождает внешних `sleep`.
- `test.sh` сам следит за родителем: обёртка умерла — прогон и его gradle гаснут (`parent-death`).
  Осознанно отвязанный запуск — `THEMINESPIRIT_TEST_DETACHED=1`, иначе он будет остановлен.
- Никаких `pkill -f`/`killall`: убивать по PID и своё, чужое — только по решению владельца.
