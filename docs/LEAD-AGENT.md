# Главный агент

Главный агент ведёт проект сам: анализирует, правит, тестирует, коммитит и сопровождает живой сервер.
Исполнители, git worktree и отдельные ветки не используются без отдельного решения владельца.

## Приоритет правил

1. Явное решение владельца.
2. [AGENTS.md](../AGENTS.md) и [ARCHITECTURE.md](ARCHITECTURE.md).
3. Правила задачи и связанные документы.
4. Конкретное задание не может ослабить правила выше.

Если задание противоречит правилам или исходные данные не подтверждены — **STOP**: не угадывать,
привести оба `file:line` и задать вопрос владельцу.

## Старт сессии

1. Прочитать [AGENTS.md](../AGENTS.md), [ARCHITECTURE.md](ARCHITECTURE.md), [README.md](../README.md)
   и [AGENT-RULES.md](AGENT-RULES.md).
2. Прочитать хвост [TestResults/progress.md](../TestResults/progress.md) и открытые пункты [todo.md](../todo.md).
3. Выполнить `git status --short`. Чужие изменения не трогать, не stash-ить и не сбрасывать.
   Документацию можно править отдельно, если её файлы не изменены другим агентом; код в грязном дереве — нет.
4. Проверить сервер только чтением: `scripts/live.sh status`.
5. Взять задачу со статусом `READY`. `BLOCKED` не исполнять.

## Рабочий цикл

- Сначала подтвердить корневую причину данными или `file:line`; чинить причину, а не симптом.
- Поведение мода менять только через граф и аудит мира: [ARCHITECTURE.md](ARCHITECTURE.md).
- Правки существующих файлов — точечные. Codegraph использовать, если он доступен; иначе — точечные Read/Grep
  без сплошного перечитывания проекта.
- Тесты — только `scripts/test.sh unit` / `gametest`. Для исправления бага тест сначала краснеет на старом коде;
  для рефакторинга и документации красный тест не требуется.
- Итерации — `unit --changed` или `unit --module <м>`; полный `unit` и `gametest --full` — один раз в финале.
- Законченный блок — один коммит. После блока записать результат в
  [TestResults/progress.md](../TestResults/progress.md).

## Git

- Работа только в `main` клона `the-mine-spirit/`. Worktree, ветки и субагенты — только по отдельному решению владельца.
- Запрещены `stash`, `reset --hard`, `clean`, `checkout`/`restore` без пути, `--amend`, `rebase` и force-push.
- Перед коммитом проверить `git status --short` и `git diff`. В индексе не должно быть чужих изменений:
  не снимать их со staging, а остановиться и согласовать коммит.
- Добавлять в коммит только свои точные пути. Push — только по прямой просьбе владельца.
- Публикация не является частью коммита или слияния. Автоматический `publish.sh` из обёрток запрещён.

## Только по согласованию

- Публикация мода и перезапуск сервера — [docs/PUBLISH.md](PUBLISH.md).
- Перед установкой `publish.sh` проверяет jar: непустой `META-INF/neoforge.mods.toml`, наличие `modId`
  и более 1000 классов.
- Push в remote и изменение версий зависимостей.
- Изменение мира игроков, откат мира и новые упрощения механик.
- Запуск `mutationTest` и другие тяжёлые переборы.

## Живая работа

- Основной сервер — только чтение через `scripts/live.sh`; ручные REST-запросы только если обёртки не хватает.
- Отладка — в своей копии: `scripts/dev-server.sh up`, затем `scripts/live-debug.sh`.
- Сначала hotswap; перезапуск копии — только если схема класса не заменяется.
- Каждое вмешательство и странность — в `live-user-test-run/incidents.md` с фактами.
- Не завершать Gradle/Java других агентов. Детектор сирот `scripts/lead/orphans-win.sh` только показывает PID,
  CPU и worktree; решение об остановке — владелец.
- Снимок мира — только серверными скриптами `server/scripts/world-snapshot.sh` и `world-restore.sh`.

## Старые обёртки `oc-results`

Каталог `../oc-results/` находится вне репозитория и содержит журналы, снимки и устаревшие инструменты
многоагентного режима. Он не является источником текущих правил.

Не запускать:

- `run-one.sh`, `next-slot.sh`, `lead-merge.sh`, `self-merge.sh`, `publish-main.sh`;
- `oc-results/live.sh` вместо `scripts/live.sh`;
- `guardrun.sh` и `fix-baseline.py` как часть текущего цикла.

Старые обёртки могут обходить проверку грязного дерева, удалять worktree с `--force`,
автоматически push-ить и публиковать мод. Если владелец решит вернуть исполнителей,
сначала нужно написать новые инструкции и обёртки под текущий режим, а не оживлять эти файлы.

## Формат задания

```text
СТАТУС: READY | BLOCKED
ЦЕЛЬ: один проверяемый результат.
ОСНОВАНИЕ: подтверждённые file:line и данные.
ФАЙЛЫ: точный список.
НЕЛЬЗЯ: publish/restart/push; worktree/branch; reset/clean/force; прямой gradlew.
СДЕЛАТЬ: 1–3 конкретных действия.
ПРОВЕРКА: точные команды и ожидаемый результат.
ГОТОВО КОГДА: критерий выполнен, тесты зелёные.
ОТЧЁТ: хэш; тесты; не сделано; техдолг.
КОНФЛИКТ ИЛИ НЕХВАТКА ДАННЫХ: STOP, не угадывать.
```

В `READY` недопустимы фразы «уточнить при старте», «например» вместо решения и незаданные критерии готовности.
Общие правила не дописываются в каждое задание автоматически: карточка ссылается на нужный документ.

## Отчёт

Коротко: хэш коммита, итог тестов, что не сделано и почему, технический долг.
«Похоже, работает» без команды, данных или `file:line` не является отчётом.
