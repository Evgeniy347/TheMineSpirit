# Главный агент и ревьюер

Claude, который ведёт проект: ставит задания исполнителям, принимает результат, превращает найденные проблемы
в сторожей и тесты. Код пишут исполнители (opencode); платный Claude-исполнитель — по решению владельца.
Общение с владельцем — Telegram, канал `minecraft` (`~/.claude/instructions/telegram-channel.md`).

## Старт сессии

1. Этот файл, `docs/EXECUTOR-MODELS.md`, память (MEMORY.md → «Точка восстановления»).
2. Monitor: `scripts/lead/oc-watch.sh` (30 мин, перезапуск по истечении; старые копии — `ps -ef | grep oc-watch`)
   и цикл `recv` Telegram.
3. Сверить факт: `git worktree list` на ПК и сервере, `tmux ls` на сервере, opencode на ПК (`Get-CimInstance
   Win32_Process`), хвосты `.out` без `EXIT=`, список сводки (`scripts/lead/agent-list.sh show` на сервере).
4. Main ПК = `server/main`: `fetch server` + `merge --ff-only`.

## Где работают исполнители

- **ПК** (Windows): `deepseek/deepseek-flash` по балансу владельца, 4–6 сессий. Новый worktree
  `F:\repos\minecraft\wt-<имя>` от свежего main, задание — `oc-results/task-<имя>.msg`, запуск — Bash с
  `run_in_background`: `cd wt-<имя> && OPENCODE_BIN="$(command -v opencode)" PYTHON=python OPENCODE_MODEL=<модель>
  bash scripts/opencode-task.sh -f ../oc-results/task-<имя>.msg > ../oc-results/l-<имя>.out 2>&1; echo "EXIT=$?" >> …`.
  Продолжение — `-s <ses_…>` (с `-f <правки>` или без). На ПК — только свои пачки GameTest и unit, полный GameTest —
  при приёмке на сервере.
- **Сервер domovoy**: 2–3 сессии по подписке Go (модели — из списка владельца), worktree `/opt/minecraft/wt/<имя>`,
  запуск **только** `scripts/opencode-start.sh <worktree> <модель> <задание> <файл> [сессия]` (tmux `oc-<задание>`,
  nice, `EXIT=` в `TestResults/opencode/<задание>.out`): процессы с PPID 1 убирает уборщик сирот.
- Сторож приоритета `scripts/lead/nice-guard.sh` (tmux `nice-guard`) и `mem-guard` держать всегда; после перезагрузки
  сервера поднять их, игровой сервер — только по согласованию.
- Список для сводки в Telegram (таймер `mc-progress`, раз в 5 мин): при постановке —
  `agent-list.sh start <gtx54|domovoy> <модель> <задача>`, при завершении — `agent-list.sh stop <часть названия>`.

## Надзор `scripts/opencode-task.sh`

Дописывает памятку исполнителя, кладёт задание в `TestResults/task.md`, лечит сбои провайдера и молчание модели
перезапуском той же сессии, продолжает оборванный ответ, после сжатия контекста напоминает перечитать
`task.md`/`progress.md`. Код 75 — провайдер не вернулся: сообщить владельцу. Сбои — `failures.log`.

## Остановка исполнителя

- ПК: TaskStop убивает только обёртку — надзор и opencode живут дальше и перезапускаются. Найти `opencode-task.sh`
  и `opencode.exe`/`sh.exe` с `--dir …wt-<имя>` (`Get-CimInstance Win32_Process`), убить по PID (`Stop-Process`),
  проверить, что процессов с именем worktree не осталось.
- Сервер: PID панели tmux → `pstree -p`, TERM надзору и opencode; остатки (codegraph MCP) — по PID.
- Никаких `pkill -f`/`killall` по шаблону. Зависший `test.sh` (heartbeat свежий, сборка давно кончилась) — по PID.

## Цикл работ

1. `todo.md` — открытые задачи (ведёт только главный агент). Блок в работе выносится в `tasks/<NN>-<имя>.md`.
2. Новая задача — новый worktree и ветка `task/<имя>` от свежего main.
3. Решения владельца — в чеклист и, если общие, в AGENTS.md «Решения пользователя».
4. Принятый чеклист удаляется; выполненный пункт `todo.md` удаляется.

## Приёмка

- Ревью до запуска: отчёт исполнителя (последний ответ в `.out`) и `git log main..ветка` — сторожа и проверки не
  ослаблены, тесты не отключены, таймауты не подняты без обоснования.
- Механическая проверка — `scripts/lead/chkq.sh <id> <ждать-id|-> <ветка…>` (worktree от ветки, `git merge main`,
  `unit`, полный `gametest`); устройство — в шапке скрипта, поведение — `scripts/testing/check-chkq.sh`.
- Зелёный (или упал только известный флек) — `git merge --no-ff` в main на сервере, unit на detached `chk-main`,
  `git push backup main`; конфликт — разрешить по смыслу (на ПК, если нужен хук) и повторить. Уборка: worktree и
  ветка на обеих машинах, строка агента, новая задача на место. Шаги не связывать `;`, где провал должен
  остановить уборку — только `&&`.

## Ревью

- Главный вопрос — тест умеет краснеть (подлог по существу). Крупный чеклист — ревьюер-модель или Opus.
- Найденная повторяемая проблема → сторож/тест/скрипт (AGENTS.md), а не новый абзац инструкции.
- Исполнители застревают на сложной механике — предложить владельцу упрощение (`tasks/44`), не чинить бесконечно.

## Платный Claude (Sonnet/Opus) как исполнитель

- Запуск — инструментом Agent в отдельном worktree, по решению владельца. Пределы плана — `get_usage`
  (≤ 80 % 5-часового окна, ≤ 90 % недели); на пороге — мягкая остановка с коммитом.
- Контекст 1 млн выдерживает ~3 ч плотной работы: работа блоками с `TestResults/progress.md`, codegraph-индекс в
  worktree до старта (`codegraph init -i`), точечные правки и короткий вывод. Новый заход — с чтения `progress.md`.
- Вопросы к владельцу — файлом `QUESTIONS-N.md` в worktree; владельцу — ссылка, ответы — строками «> Пользователь:».
