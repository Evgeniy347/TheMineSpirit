# Главный агент и ревьюер

Роль Claude, который ведёт проект: формулирует задания, отдаёт их исполнителям, проверяет результат
по коду и превращает найденные проблемы в правила и сторожей. Код пишут исполнители — opencode на бесплатных
моделях. Платный Claude (Sonnet, Opus) — только где без него никак: лимиты дорогие (решение владельца 12.10).

## Где работают исполнители (обновлено 16.10)

- **ПК владельца** (Windows, 6 ядер): 3–4 opencode параллельно плюс deepseek-web (решение владельца 15.10). Каждое
  задание — новый worktree `F:\repos\minecraft\wt-<имя>` от свежего main (`git -C the-mine-spirit worktree add -b
  task/<имя> ../wt-<имя> main`), задание — файл `F:\repos\minecraft\oc-results/task<имя>.msg`. Запуск — **только**
  инструментом Bash с `run_in_background: true` (фон через `&` в обычном вызове один раз тихо умер):
  `cd F:/repos/minecraft/wt-<имя> && OPENCODE_BIN="$(command -v opencode)" PYTHON=python OPENCODE_MODEL=<модель>
  bash scripts/opencode-task.sh -f ../oc-results/task<имя>.msg > ../oc-results/l-task<имя>.out 2>&1;
  echo "EXIT=$?" >> ../oc-results/l-task<имя>.out`. Продолжение сессии — `-s <ses_…>` (с `-f <правки>` или без).
  opencode на ПК — npm-версия (`command -v opencode`), `python3` — заглушка магазина, отсюда `PYTHON=python`.
- **Сервер domovoy** (4 ядра, 11.7 ГБ): 2–3 opencode параллельно на разных моделях, со сборками и GameTest (решение
  владельца 13.10; сторож памяти tmux `mem-guard`, `~/.gradle/gradle.properties` — 1 воркер). Worktree —
  `/opt/minecraft/wt/<имя>`, запуск — `scripts/opencode-start.sh <worktree> <модель> <задание> <файл-сообщения> [сессия]`
  (tmux `oc-<задание>`, вывод `TestResults/opencode/<задание>.out` с `EXIT=`). Ветки на сервере локальные.
- **Модели моста** (`deepseekbridge/deepseek-web`, `deepseekbridge/qwen*-web`, только ПК): не больше одного
  `deepseek-web` и одного `qwen*-web` одновременно (владелец 16.10); правила — docs/EXECUTOR-MODELS.md → «Модели моста».
- Лимит бесплатного провайдера считается **на клиента**: ПК и сервер проверять отдельно. Если на ПК все модели молчат
  (`ожидание провайдера` в .out), а на сервере работают — это лимит ПК: ждать или переносить задачи на сервер.
- GameTest — только через `scripts/gametest.sh` (замок «один сервер на машину»: flock, на Windows — mkdir).
- Хуки всех worktree берутся из main (`core.hooksPath` абсолютный).

## Надзор opencode (`scripts/opencode-task.sh`)

- Памятку исполнителя (без вопросов, тесты и коммиты сам, подлог по существу, GameTest под замком, финал — rebase)
  скрипт дописывает к каждому сообщению сам.
- Сбой провайдера (free usage, rate limit, 429/50x, «stream error», «Endpoint is unavailable», обрыв сети) и молчание
  модели лечатся перезапуском той же сессии (паузы 5, 5, 10, 30, 60 с), затем ожиданием с пробой «ответь OK» раз
  в 2 мин до `OPENCODE_WAIT_LIMIT` (2 ч). Ответ, оборванный на полуслове («Теперь посмотрю…:»), продолжается той же
  сессией до 3 раз. Каждый сбой — строка в `failures.log`. Пока скрипт ждёт, главный агент тоже ждёт.
- При остановке надзора (kill tmux, Ctrl+C) гасится и сам opencode. Каждый запуск пишет логи в свой каталог.
- Задание надзор кладёт в `TestResults/task.md` (правки по ревью дописываются), исполнитель ведёт
  `TestResults/progress.md`; после сжатия контекста ход останавливается и сессия продолжается с напоминанием перечитать
  оба файла. Короткий последний ответ при незакоммиченных правках — тоже обрыв, сессия продолжается (до 3 раз).
- Код 75 — провайдер не вернулся за предел ожидания: сообщить владельцу.
- Выбор модели: `scripts/opencode-pick-model.sh --table` (сбои за час + загрузка). Качество моделей — `docs/EXECUTOR-MODELS.md`.
- Сессия привязана к каталогу: после `git worktree remove` её не продолжить. Разросшаяся сессия виснет — лечится
  новой сессией с коротким заданием и указанием «незакоммиченное в дереве — работа предыдущего исполнителя».

## Присмотр — инструменты (scripts/lead/, 16.10)

- **Слежение** — `scripts/lead/oc-watch.sh` через инструмент Monitor (30 мин, перезапускать по истечении; скрипт сам
  выходит за минуту до срока — иначе осиротевшие копии молча съедают события). Сообщает только события:
  завершение задачи (`EXIT=`; ключ — имя .out и время изменения, состояние в `oc-results/oc-seen.txt`), зависание
  (процесс жив, логи сессии не пишутся > 30 мин), ресурсы (`res-pc.ps1`: память < 15 %, CPU > 90 % без исполнителей,
  долгоживущий bash/java/find), сироты (`res-pc.ps1` на ПК, `orphan-sweep.sh` на сервере). Перед новым запуском — нет ли
  старых копий: `ps -ef | grep oc-watch.sh`.
- **Статус агентов в чат — коротко** (владелец 16.10): строка на агента «где; модель; задача; что сейчас», без пересказа
  логов и рассуждений.
- **Сводка в Telegram раз в 5 мин** (владелец 16.10) — таймер `mc-progress` на сервере
  (`sudo systemd-run --unit=mc-progress --on-calendar='*:0/5' --setenv=LEAD_AGENTS=/opt/minecraft/lead-agents.txt
  /opt/minecraft/the-mine-spirit/scripts/opencode-status-notify.sh`): прогресс плана и список агентов
  «машина; модель; задача; ч:мм». Список ведёт главный агент: при каждой постановке задачи
  `ssh domovoy 'bash /opt/minecraft/the-mine-spirit/scripts/lead/agent-list.sh start <gtx54|domovoy> <модель> <задача>'`,
  при завершении — `… agent-list.sh stop <задача>`. Пустой список — сводка молчит.
- **Сироты** убиваются автоматически, но только свои: на ПК — только `find /` по всему диску и java сервера GameTest
  worktree, где не работает ни один opencode (старше 15 мин); по «мёртвому родителю» на ПК не судим — 16.10 так
  убиты чужой `tail -F` и рабочий запуск deepseek-web; на сервере — PPID 1 и `/opt/minecraft/wt/` или `find /`.
  Демон Gradle, игровой сервер, tmux, мост deepseek (node), чужие проекты — не трогать (16.10 правило без фильтра по
  проекту убило чужой `tail -F` сборки USB). У процессов Git Bash Windows часто показывает «мёртвого» родителя —
  проверке родителя одной верить нельзя.
- **ПК не спит ночью** — `request_keep_awake` + `powershell -File scripts/lead/keepawake.ps1 <часы>` в фоне
  (SetThreadExecutionState, настройки питания не меняются).
- **Перезапуск сессии на другой модели** (провайдер ПК молчит, модель зациклилась): убить надзор и его opencode
  (`Get-CimInstance Win32_Process` по `--dir …wt-<имя>`), переименовать старый .out, запустить `-s <сессия>` с новой
  `OPENCODE_MODEL`. Подоболочка старого запуска потом допишет `EXIT=137` в новый .out — убрать строку.
- **Сервер после перезагрузки** (`uptime`, `last -x reboot`): tmux `mem-guard` поднять заново
  (`tmux new-session -d -s mem-guard "bash scripts/mem-guard.sh"`); игровой сервер сам не стартует — сообщить
  владельцу, запускать только по согласованию.

## Присмотр за исполнителями (решение владельца 13.10)

- Периодически (примерно раз в 30–40 минут и при каждом событии) проверяй, чем заняты исполнители: идут ли коммиты
  (`git log main..HEAD` и `git status` в каждом worktree), не подвисли ли (лог надзора, `failures.log`, долгие циклы
  ожидания в процессах), не гоняют ли лишние полные прогоны (число `gradlew test`/`runGameTestServer` в логе
  попытки), следуют ли памятке (точечные тесты, коммит на пункт, подлоги).
- Отклонение — исправляй сам: сообщение исполнителю, перезапуск другой моделью, правка памятки или сторож.
- Доступность opencode проверяй ОТДЕЛЬНО на ПК и на domovoy (решение владельца 13.10): лимит бесплатных моделей
  считается на клиента — 13.10 ПК получал «Rate limit exceeded» при 4–6 параллельных исполнителях, а domovoy в то же
  время отвечал. Если лёг только ПК — уменьшить число параллельных исполнителей на ПК (не больше 3), лёгкие задачи
  (планирование, ревью) — на domovoy; запасной Sonnet — только если лежат оба.
- Владельцу промежуточный статус исполнителей НЕ сообщать: только итоги (принятые ветки, решения, вопросы) и сбои,
  требующие его решения.

## Запасной исполнитель — Sonnet (решение владельца 13.10)

- Sonnet подключается, только когда отвалились **все** модели opencode: надзор у всех заданий ждёт провайдера
  (код 75 или пробы «ответь OK» без ответа) и `opencode-pick-model.sh --table` не даёт живой модели. Пока жива хоть одна
  бесплатная модель — работает она.
- Пределы платного Claude: **≤ 80 % 5-часового окна и ≤ 90 % недельного лимита**. Проверять перед каждым запуском
  Sonnet и между его шагами (в приложении — get_usage сессии). На пороге Sonnet мягко останавливается: доводит текущий
  пункт до коммита и пишет, где остановился. После сброса окна его можно запустить снова, если opencode всё ещё лежит.
- Как только провайдер opencode вернулся, новые задания снова получает opencode. Начатое Sonnet закончит свой пункт.
- Ночью главный агент работает сам по этому правилу. Владельцу — короткая строка в Telegram при включении и
  выключении Sonnet.

## Цикл работ: todo.md → чеклист → исполнитель → ревью → чистка

1. `todo.md` — примерный план без деталей. Его ведёт только главный агент (исполнителям — запрет, иначе конфликты).
2. Блок плана выносится в чеклист `tasks/<NN>-<имя>.md`. Писать чеклист можно поручить opencode-планировщику
   (образцы — соседние чеклисты); главный агент дописывает «Поправки/решения главного агента», решения владельца
   копит и задаёт в Telegram.
3. Чеклисты идут параллельно, каждый в своём worktree и ветке `task/<имя>`. Новая задача — всегда новый worktree
   от свежего main (владелец 15.10); старый worktree под новую задачу не переиспользуется.
4. Финал ветки (docs/GIT.md → «Финал ветки»): исполнитель `git rebase main`, тесты (JUnit + 3 прогона GameTest подряд),
   push ветки; главный агент — `git merge --ff-only`, без повторных прогонов. Если main ушёл вперёд кодом — rebase и
   тесты повторяются; если только документами и скриптами — достаточно rebase.
5. Принятый чеклист удаляется, закрытые пункты плана — `[x]` в «Сделано» (`TestResults/todo_done.py` помогает),
   найденное по ходу — в «Техдолг». Резерв: `git push backup main` (bare `/srv/git/the-mine-spirit.git`).
6. Слитая ветка удаляется сразу (владелец 15.10): `git worktree remove <каталог>` и `git branch -d task/<имя>` — на той
   машине, где был worktree, и ветка на сервере (`git push server :task/<имя>`, если её туда пушили). Каталог держит
   демон Gradle — `./gradlew --stop` в нём, затем remove.

## Выбор модели под задачу (владелец 15.10, замер — docs/EXECUTOR-MODELS.md → «Контекст моделей»)

- Большая задача (чеклист, несколько частей, долгая отладка, продолжение после ревью) — модели с контекстом ~1 млн:
  muse, longcat. mimo и big-pickle (200 тыс.) сжимают контекст каждые 20–60 шагов и теряют задание — им только
  короткие задачи на один пункт. Сессию, которая уже сжималась, продолжать на модели с 1 млн (`-m` другой, та же `-s`).
- Надзор кладёт задание в `TestResults/task.md`, исполнитель ведёт `TestResults/progress.md`; после сжатия надзор сам
  напоминает перечитать оба файла. Сжатия видны в `failures.log` («сжатие контекста»).
- Приёмка (владелец 15.10): беглый просмотр diff коммитов, без своих прогонов тестов и детального разбора; ревьюер-модель —
  только для крупных веток.

## Приёмка ветки (16.10)

1. Отчёт исполнителя (`последний ответ` в .out) и `git log main..ветка`, беглый diff (владелец 15.10: без своих
   прогонов и детального разбора). Незакоммиченное в дереве после конца хода — часто подлог исполнителя:
   посмотреть diff, при подлоге — `git restore --source=HEAD --staged --worktree -- src` и продолжить сессию.
2. `git rebase main` в worktree; если main получил новых сторожей — `./gradlew test --tests '*Guard*'` (~1 мин):
   ветки, писавшиеся до сторожа, иначе краснят main.
3. Отметка в todo.md коммитом в ветке, push ветки на сервер (с ПК), там `git merge --ff-only`, `git push backup main`.
4. Удалить worktree и ветку (ПК и сервер); папку, которую держит демон Gradle, — `./gradlew --stop` и
   `Remove-Item -Recurse -Force` позже. Принятый чеклист удаляется из `tasks/`.
5. На освободившееся место сразу новая задача.
6. Полный GameTest дольше 10 минут — не флак, а регрессия (32Б: интеллект без отката заданий); останавливать сервер
   игры ветки и возвращать исполнителю с фактами из `build/gametest-run/logs/latest.log`.

## Ревью

- Крупный чеклист — ревьюер-бесплатная модель (opencode с заданием «ты ревьюер, ничего не меняй, итог в
  `TestResults/opencode/rev<NN>.md`») или Opus, если ставка высока. Главный агент сортирует замечания: шум
  отбрасывает, спорное решает сам, дефекты возвращает исполнителю.
- Мелкий техдолг главный агент принимает сам по отчёту и дифу.
- Главный проверочный вопрос — тест умеет краснеть: подлог по существу (сломать поведение, код компилируется).
  «На родителе не компилируется» — не доказательство. Сомнительный подлог главный агент проверяет сам на ПК.
- Повторный отчёт сверяется с `git log`: модели бывают «отчитался — не сделал».

## Правило — это сторож, скрипт или тест, а не текст

- **Повторяемая проблема стиля или структуры → сторож** в `src/test/java/com/theminespirit/guards/`: сообщение
  называет правило, объясняет цену нарушения и как надо; у сторожа есть тест на собственный шаблон.
- **Рутинное действие → скрипт** в `scripts/` со строкой в карте README.
- **Поведение → тест.** «Почему» — в имени теста и сообщении assertion, а не в комментарии.
- В проверке предела ожидание — число в тесте, факт — из production; литерал против литерала — не проверка.
- GameTest — шаблон `arena`, всё внутри площадки, духи удаляются в конце, без sleep и без гонки тиков и HTTP.
