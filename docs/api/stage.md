### GET /v1/settlement/stage

Текущий этап поселения и почему он такой. Этап считается по **аудиту мира** против плана: он стоит на
первом этапе, у которого мир не подтверждает хотя бы одну обязательную постройку. Журнал доски этап не
закрывает. Ответ:

```json
{ "stage": 2, "stages": 4,
  "missing": {"BUILD_MINE": 2},
  "requirements": [
    {"stage": 1, "id": "BUILD_HOUSE", "level": 1, "closed": true, "world": "ready", "optional": false},
    {"stage": 1, "id": "BUILD_MINE", "level": 1, "closed": true, "world": "not_ready", "optional": false},
    {"stage": 2, "id": "BUILD_MINE", "level": 2, "closed": false, "world": "unknown", "optional": false}
  ] }
```

- `stage` — этап, на котором стоит поселение; `stages + 1` значит «все этапы закрыты»;
- `missing` — остаток текущего этапа по миру (чего мир не подтвердил до закрытия);
- `requirements` — постройки и обязательные (`optional: false`), и желательные (`optional: true`) этапов до
  текущего включительно; `world` — `ready`, `not_ready`, `unknown`, а `closed` — отметка журнала для сравнения.
  Желательные переход не держат. Смена этапа принимается после трёх одинаковых аудитов подряд, поэтому один
  сбой не дёргает этап.

### POST /v1/settlement/stage

Откат этапа (и `PUT` — то же самое). Мир не ломается: постройки не сносятся, с доски снимаются задания более
высоких этапов, снимаются отметки журнала, а постройки целевого этапа, не готовые по миру, снова открываются на
ремонт обычным расписанием духа. Тело:

```json
{ "request_id": "3f1c2d3e-0000-4000-8000-000000000000", "stage": 1,
  "by": "owner", "reason": "шахта 96%, двор 91% — этап не закрыт целиком" }
```

- `request_id` — обязателен, UUID; повтор с тем же телом возвращает прежний ответ, с другим — 409 `conflict`;
- `stage` — обязателен, целевой этап (с первого); вперёд этап не ставится — он закрывается постройкой;
- `by` — кто откатил, по умолчанию `rest`; попадает в карточку `[stage] откат 2→1: причина …, кем …`;
- `reason` — причина, по умолчанию `откат этапа`;
- лишнее поле — 400 `invalid_request` с именем поля.

Ответ `200`:

```json
{ "previous": 2, "stage": 1, "changed": true,
  "forgotten": ["building:BUILD_MINE:1", "building:BUILD_WAREHOUSE:2"],
  "cancelled": ["graph:building:plaza"], "request_id": "3f1c2d3e-…" }
```

- `forgotten` — снятые отметки журнала (по ним этап возвращается назад);
- `cancelled` — задания более высоких этапов, снятые с доски;
- повторный откат на текущий этап — успех с `changed: false`, доска не меняется.

Отказ `409 conflict`: этап вперёд, целевой этап закрыт по миру целиком (откатывать нечего) или этап вне
списка. Отказ не трогает ни одной отметки и ни одного задания.

Откат переживает перезапуск: снятие отметок пишется в журнал досок (`REOPENED`), а состояние доски сохраняется
в данных мира. Выполняется на серверном потоке, как и остальные изменения мира.

### GET /v1/settlement/warehouse

Склад поселения: нужен ли он на текущем этапе, где он стоит и сколько места в нём. Стратег читает это перед
решением. Ответ:

```json
{ "stage": 2, "required_level": 2, "built_level": 1, "needed": true,
  "order": {"level": 2, "site": "10,64,-3", "by": "strategist", "reason": "места мало", "tick": 1200},
  "plan_site": "10,64,-3",
  "materials": {"oak_planks": 64, "cobblestone": 128, "chest": 16} }
```

- `required_level` — уровень склада, который требует текущий этап (`stages.json`);
- `plan_site` — место `storage` из плана поселения или `null`, если плана нет: его можно передать в `POST` без
  поиска координат;
- `built_level` — наибольший уровень, отмеченный аудитом мира;
- `needed` — журнал или решение стратега требуют уровня выше построенного;
- `order` — решение стратега или `null`, если его ещё нет; без решения граф склад сам не строит;
- `materials` — материалы схемы нужного уровня (для повышения — разница уровней в задании графа).

### POST /v1/settlement/warehouse

Решение стратегического ИИ: когда, где и какого уровня строить или улучшать склад. Мод и граф только исполняют:
ставят задание доски, снабжают материалами и строят по схеме. Тело:

```json
{ "request_id": "3f1c2d3e-0000-4000-8000-000000000000", "level": 2,
  "site": "10,64,-3", "by": "strategist", "reason": "склад двора полон" }
```

- `request_id` — обязателен, UUID; повтор с тем же телом возвращает прежний ответ, с другим — 409 `conflict`;
- `level` — уровень склада 1..4; граф строит следующий уровень от уже построенного;
- `site` — место `"x,y,z"` внутри плана поселения; при повышении уровня место не меняется — другое место даёт
  409 `conflict`;
- `by`/`reason` — кто и зачем решил, попадают в карточку журнала;
- лишнее поле — 400 `invalid_request`.

Ответ `200`: `previous` (прежнее решение или `null`), `order`, `changed`, `request_id`.

#### Откат для владельца

```bash
curl -s -X POST http://127.0.0.1:8765/v1/settlement/stage \
  -H 'Content-Type: application/json' \
  -d "{\"request_id\":\"$(uuidgen)\",\"stage\":1,\"by\":\"owner\",\"reason\":\"шахта 96%, двор 91%\"}"
```

Сначала посмотреть, что происходит: `curl -s http://127.0.0.1:8765/v1/settlement/stage`.
