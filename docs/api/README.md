# API духов (bridge) — контракт v1

Мост живёт внутри мода и обслуживает контракт встроенным HTTP-сервером JDK. Реализованы все конечные точки:
`capabilities`, `health`, `bots`, `bots/{id}`, `observe`, задачи, события и `plan`. Ядро `core` обслуживает контракт, но не
зависит от HTTP.

## Общие правила

- База: `/v1`, формат JSON (UTF-8), кроме потока событий (`text/event-stream`). Ответы идут с
  `Content-Type: application/json; charset=utf-8` и `Cache-Control: no-store`.
- Авторизации нет: сеть доверенная (решение пользователя 2026-10-11); доступ ограничивается адресом привязки
  (`bindAddress` в `serverconfig/theminespirit-rest.toml`) и файрволом.
- Тело запроса — не больше 1 МиБ; больше — 400 `invalid_request`.
- Лимиты запросов (на адрес клиента; адрес в лог не пишется):

| Что | Предел | Отказ |
|---|---|---|
| частота запросов | ведро 40, пополнение 20 в секунду | 429 `rate_limited`, заголовок `Retry-After` в секундах |
| одновременные потоки событий | 4 | 429 `rate_limited` |
| одновременные наблюдения `observe` | 4 | 429 `rate_limited` |
| тело запроса | 1 МиБ | 400 `invalid_request` |
| узлов в плане / глубина | 256 / 16 | 422 `invalid_plan` |
| завершённых задач в реестре | 256 (активные не вытесняются) | старейшие вытесняются |

- Идемпотентность: изменяющие запросы несут `request_id` (UUID). Повтор с тем же `request_id` возвращает
  прежний результат, а не выполняет действие заново.
- Лимиты плана (проверяются валидатором): `repeat.times` 1..64, глубина дерева ≤ 16, число узлов ≤ 256.
- Ошибки — единый объект:

```json
{"error":{"code":"invalid_plan","message":"У скрипта 'wait' не задан обязательный параметр 'ticks' (INT)","details":{}}}
```

`details` — всегда объект (может быть пустым). Тексты — на русском (см. CONVENTIONS.md → «Ошибки»).

| Код | HTTP-статус | Когда |
|---|---|---|
| `invalid_request` | 400 | неверное тело, поле или тип поля; тело больше лимита; 405 (см. ниже) |
| `forbidden` | 403 | зарезервирован, пока не выдаётся |
| `not_found` | 404 | неизвестный путь или дух |
| `conflict` | 409 | состояние не позволяет действие: наблюдение мёртвого духа, дух занят задачей, `request_id` уже использован с другим телом |
| `invalid_plan` | 422 | план не прошёл валидацию |
| `rate_limited` | 429 | больше 4 наблюдений (`observe`) или 4 потоков событий одновременно, либо частота запросов выше лимита |
| `internal` | 500 | сбой моста; сервер не ответил на задачу в серверном потоке за отведённое время |

Известный путь с чужим методом даёт 405 с кодом `invalid_request` и заголовком `Allow` (методы через запятую).
Кода `unauthorized` нет.

## Ресурсы

- **Bot** — дух: `id` (UUID сущности), `name`, `state` (`idle`/`busy`/`dead`), `position` (`[x, y, z]` — блок духа),
  `dimension`, `current_task` (`task_id` активной REST-задачи, иначе `id` задания или карточки занятия доски, иначе
  занятие/скрипт; `null` только у простоя), `food` (доля шкалы голода, `[0; 1]` — `1.0` сыт, `0.0` голоден).
  Состояние `dead` — дух не жив, `busy` — у него идёт задача, иначе `idle`.
- **Observation** — текстовая модель мира вокруг духа (не картинка): позиция, инвентарь, перечень блоков
  в радиусе, сущности, контейнеры, предмет в руке, здоровье и сытость, задание доски, выпавшие предметы,
  содержимое контейнеров, время суток, `hash`.
- **Task** — поставленная цель и/или готовый план; статус, прогресс, результат.
- **Capability** — описание скрипта: `id`, `summary`, `params` (JSON-Schema), предусловия (`preconditions` — текст
  для человека), структурные требования `requires` (что должно быть у духа, например кирка нужного уровня) и эффекты.
- **Decision** — запись журнала решений тактики: тик, дух, «было → стало» по полю `decision` / `mode` / `target` /
  `order`, сработавшее правило или топ-3 фактора с весами, ключевые факты (враги рядом, здоровье, броня, оружие).
- **BoardTask** — задание доски поселения: `id`, `case`, `priority`, `assignee` (держатель или `null`), `status`,
  `requiredItems` (гейт), `missing` (нехватка по снимку запасов), `dependsOn`, `createdAt`, `level`, `cause`.
- **UnprotectArea** — разрешённая область: внутри неё `BlockProtection` не считает блоки постройкой игрока.
  `id` (UUID, назначает мод), `dimension`, `min` и `max` (`[x, y, z]`), `granted_by` (кто попросил),
  `granted_at` (миллисекунды UTC), `reason`, `expires_at` (миллисекунды UTC или `null` — бессрочно).
  Осторожная защита вне области и для всего остального (чёрный список, защищённые зоны) не меняется.

## Конечные точки

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/v1/capabilities` | каталог скриптов (для ИИ-планировщика) |
| GET | `/v1/health` | возраст серверного тика и признак зависания ([health.md](health.md)) |
| GET | `/v1/bots` | список духов и их состояние |
| GET | `/v1/bots/{id}` | состояние одного духа |
| GET | `/v1/spirits/{id}/decisions` | журнал решений тактики духа (почему он так поступил) |
| GET | `/v1/graph/decisions` | последнее объяснение решений графа ([graph.md](graph.md)) |
| POST | `/v1/bots/{id}/observe` | наблюдение мира вокруг духа |
| POST | `/v1/bots/{id}/tasks` | поставить цель (и/или план) |
| GET | `/v1/tasks/{id}` | статус, прогресс, результат |
| DELETE | `/v1/tasks/{id}` | отменить задачу (мир остаётся консистентным) |
| GET | `/v1/tasks/{id}/events` | поток событий задачи (SSE) |
| POST | `/v1/plan` | сухой прогон: проверить план без исполнения |
| GET | `/v1/board` | очередь заданий доски поселения (порции, фильтры, курсор) |
| GET | `/v1/board/log` | последние записи журнала выполненных заданий |
| POST | `/v1/board/tasks` | поставить задание поселения на доску (с гейтом по ресурсам) |
| DELETE | `/v1/board/tasks/{id}` | отменить задание доски (зависимые тоже снимаются) |
| GET | `/v1/policy/unprotect` | список разрешённых областей (постройки игрока внутри них не защищены) |
| POST | `/v1/policy/unprotect` | выдать разрешение снять защиту построек игрока в области |
| DELETE | `/v1/policy/unprotect/{id}` | снять разрешение (защита области возвращается) |
| GET | `/v1/world` | лишнее, рельеф и повреждённые постройки на входе графа ([world.md](world.md)) |
| GET | `/v1/settlement/stage` | текущий этап поселения и готовность его построек по миру |
| POST | `/v1/settlement/stage` | откатить этап поселения (мир и постройки остаются) |
| PUT | `/v1/settlement/stage` | то же, что `POST` (откат этапа) |
| GET | `/v1/settlement/warehouse` | нужен ли склад, его уровень, место и материалы |
| POST | `/v1/settlement/warehouse` | решение стратега: где и какого уровня строить/улучшать склад |
| PUT | `/v1/settlement/warehouse` | то же, что `POST` (решение о складе) |
